## 大模型流式输出中 SSE 与 WebSocket 的选型逻辑、优缺点及适用场景（结合高并发、跨端兼容）

### 1. 两种协议速览

| 维度 | SSE（Server-Sent Events） | WebSocket |
| --- | --- | --- |
| 通信方向 | 单向（服务端 → 客户端） | 双向全双工 |
| 底层协议 | HTTP（长连接） | HTTP 升级握手后转为独立 TCP 帧 |
| 数据格式 | 文本（UTF-8） | 文本 + 二进制 |
| 浏览器 API | `EventSource` | `WebSocket` |
| 断线重连 | 浏览器自动重连 + `Last-Event-ID` | 需手动实现重连 |
| 连接数限制 | HTTP/1.1 同域约 6 个（HTTP/2 无此限） | 无浏览器同域限制 |
| 代理/CDN/网关 | 兼容好（本质是 HTTP） | 需代理支持 Upgrade，兼容性差 |
| 复杂度 | 低 | 高（需管理连接生命周期、心跳、重连） |

### 2. 选型逻辑：大模型流式输出为什么默认选 SSE

大模型流式输出的本质是**"服务端持续推 token，客户端只收不发"**的单向场景。选型先看通信方向：

| 场景特征 | 选型 |
| --- | --- |
| 单向推送（文本流式生成） | **SSE**（够用、简单、HTTP 生态友好） |
| 需双向交互（中途下指令、多端实时协同、语音双向） | **WebSocket** |
| 需二进制（音频流、视频帧） | **WebSocket** |

> 经验：90% 的"打字机式"文本流式问答用 SSE 即可；只有需要客户端在生成过程中向服务端发消息（如实时打断指令、多用户协同编辑）才上 WebSocket。

### 3. 高并发维度

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 水平扩展 | 本质 HTTP，网关/CDN/负载均衡天然兼容，易加节点 | 长连接有状态，需 sticky session 或共享会话层，扩展难 |
| 连接管理 | 连接即 HTTP 请求，复用网关超时/限流能力 | 需自建连接管理、心跳、重连，组件多 |
| 资源占用 | 每连接一个 HTTP 长连接（轻） | 每连接一个独立 TCP（重，需管理 buffer） |
| QPS 扩展 | 无状态部分易拆，配合 `Last-Event-ID` 重连 | 有状态，扩缩容要处理连接迁移 |
| 兼容 HTTP/2 | 多路复用，同域连接数不再是瓶颈 | 与 HTTP/2 关系复杂，部分环境需降级 |

> 高并发（QPS≥1000）下 SSE 的扩展链路见 [[6.高并发QPS≥1000下SSE长连接的复用、心跳检测、超时释放及OOM优化]]。

### 4. 跨端兼容

| 端 | SSE（EventSource） | WebSocket |
| --- | --- | --- |
| PC 浏览器 | 原生支持 | 原生支持 |
| APP（WebView） | 基本支持 | 支持 |
| 小程序（微信等） | **常不支持** EventSource，需 fetch 流式读流降级或 polyfill | 原生 `wx.connect` 支持较好 |

> 小程序是 SSE 的最大兼容坑：EventSource 不可用时，退化为用 `fetch` + `ReadableStream` 读流（部分小程序也需原生插件），或直接上 WebSocket。多端兼容方案见 [[9.多端小程序、APP、PC流式输出的兼容性处理及渲染卡顿解决方案]]。

### 5. 适用场景总结

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 文本流式问答（打字机） | SSE | 单向、简单、HTTP 生态 |
| 高并发公开服务 | SSE | 易扩展、网关友好 |
| 多端含小程序 | SSE + 降级 / WebSocket | 兼容性兜底 |
| 实时协同/中途指令 | WebSocket | 需双向 |
| 语音/视频流 | WebSocket | 需二进制 |

### 6. 一句话总结

大模型流式输出默认选 **SSE**——它是单向推送、HTTP 生态友好、高并发易扩展、浏览器自动重连；只有需要双向交互或二进制流时才上 **WebSocket**；小程序等 EventSource 不支持的端需降级方案。前端流式渲染策略另见场景架构问题目录的《11.大模型API响应延迟超1秒时的前端优化策略》。
