## 跨服务流式透传的日志埋点设计及全链路追踪实现

> LLM 流式请求常跨多服务：网关 → 业务服务 → 推理服务 → 上游 LLM。流式是多事件、长持续、跨服务的调用，传统单次请求追踪不够用，需要流式专用的全链路追踪。

### 1. 跨服务流式透传的追踪需求

```
客户端 ──→ 网关 ──→ 业务服务 ──→ 推理服务 ──→ 上游 LLM
  ↑          ↑          ↑            ↑           ↑
  └──────────┴──────────┴────────────┴───────────┘
              traceId 贯穿全链路，每跳埋点
```

| 难点 | 说明 |
| --- | --- |
| 多事件 | 一次请求产出几十~几百个流式事件，不是一次响应 |
| 长持续 | 流式持续数秒~数十秒，传统"请求-响应"span 模型不够 |
| 跨服务 | 每跳都要透传 traceId，否则链路断裂 |
| 异步透传 | 流式是异步逐段透传，埋点要跟着事件走 |

### 2. 日志埋点设计

每跳、每个关键事件都要埋点：

| 埋点字段 | 说明 |
| --- | --- |
| traceId | 全链路唯一，贯穿所有服务 |
| spanId | 当前 span 唯一 |
| parentSpanId | 父 span，串联调用层级 |
| event id | 流式事件级唯一标识（自增） |
| 时间戳 | 事件发生时间 |
| token 数 | 本事件/累计 token 数 |
| 状态 | ok / error / 中断 |
| 耗时 | 本跳/本事件耗时 |
| 服务名 | 网关/业务/推理/上游 |
| 方向 | request / response / stream-event |

### 3. 全链路追踪实现

| 实现点 | 做法 |
| --- | --- |
| traceId 贯穿 | 网关生成 traceId，通过请求头（如 `X-Trace-Id`）透传到下游每跳 |
| span 串联各服务 | 每跳创建子 span，parentSpanId 指向上游，形成调用树 |
| 流式事件级 span | 一次流式请求作为一个父 span，每个/每批事件作为子 span |
| OpenTelemetry 适配 | 用 OTel 的 Span 事件（events）记录流式事件，或自定义流式 span |
| 异步透传 | 流式透传时把 traceId 附在每个 chunk 的元数据里，下游继续埋点 |

```
traceId: abc123
├─ span: gateway (12.3s)
│  ├─ span: business-service (12.1s)
│  │  ├─ span: inference-service (11.8s)
│  │  │  ├─ event: first-token (T+0.8s)
│  │  │  ├─ event: stream-chunk#1 (T+1.0s, tokens=12)
│  │  │  ├─ event: stream-chunk#2 (T+1.2s, tokens=15)
│  │  │  └─ event: done (T+11.8s, total=320)
```

### 4. 埋点字段表（示例）

| event id | 服务 | 方向 | 时间戳 | token | 状态 | 耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| e1 | 网关 | request | 10:00:00.000 | — | ok | — |
| e2 | 业务 | request | 10:00:00.050 | — | ok | 50ms |
| e3 | 推理 | first-token | 10:00:00.800 | 5 | ok | 750ms |
| e4 | 推理 | stream-chunk | 10:00:01.000 | 12 | ok | — |
| e5 | 业务 | stream-chunk | 10:00:01.010 | 12 | ok | 10ms(透传) |
| e6 | 网关 | stream-chunk | 10:00:01.015 | 12 | ok | 5ms(透传) |
| e7 | 推理 | done | 10:00:11.800 | 320 | ok | 11.8s |

### 5. 追踪可视化与排障价值

| 价值 | 说明 |
| --- | --- |
| 定位慢节点 | 看 each span 耗时，一眼定位是网关/业务/推理/上游慢 |
| 首 token 延迟分析 | first-token span 单独看，定位首字慢的根因 |
| 流式中断定位 | 中断事件的状态+位置，定位哪一跳断的 |
| token 计费核对 | 累计 token 数贯穿全链路，对账计费 |
| 异常率统计 | 按服务/错误类型聚合，监控健康度 |
| 跨服务透传验证 | traceId 断裂即说明某跳没透传，可修 |

### 6. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| traceId 强制透传 | 网关必须生成并透传，下游没收到则自己补，不能断 |
| 流式 span 别过细 | 每个事件一个 span 数据量爆炸，可按批（如每 N 个事件）合并 |
| 采样策略 | 高 QPS 下对流式 span 采样，关键事件（first-token/done/error）必采 |
| 异步埋点不阻塞主链 | 埋点异步上报，别拖慢流式透传 |
| 与消息有序性配合 | 流式透传的事件有序性保障见 [[5.多轮对话+流式输出的消息有序性、上下文完整性保障及跨服务流式透传实现]] |

### 7. 一句话总结

跨服务流式追踪 = **traceId 贯穿全链路（网关→业务→推理→上游）+ span 串联各服务 + 流式事件级埋点（event id/时间戳/token/状态/耗时）+ OpenTelemetry 适配**，解决流式多事件、长持续、跨服务的追踪难题，用于定位慢节点、首 token 延迟、流式中断与 token 计费核对。跨服务透传的有序性配合 [[5.多轮对话+流式输出的消息有序性、上下文完整性保障及跨服务流式透传实现]]。
