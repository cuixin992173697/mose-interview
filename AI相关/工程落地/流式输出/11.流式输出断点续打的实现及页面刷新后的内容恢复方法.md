## 流式输出断点续打的实现及页面刷新后的内容恢复方法

> 流式生成中途断了（网络抖动/用户刷新/模型报错），能否从断点继续而不重头再来？本篇讲断点续打与页面刷新恢复。与网络层重连的区别见文末。

### 1. 断点续打 vs 网络重连（先厘清概念）

| 维度 | 网络重连恢复（[[2.流式返回中网络中断重连的上下文恢复方法及防重复、防丢包策略]]） | 断点续打 + 刷新恢复（本篇） |
| --- | --- | --- |
| 关注层 | 网络传输层 | 应用层 |
| 触发 | 网络中断后自动重连 | 用户主动中断/刷新/报错后续打 |
| 目标 | 连接恢复 + 防丢包防重复 | 从断点继续生成 + 刷新后内容不丢 |
| 手段 | Last-Event-ID/offset 重连续传 | resume token + 内容持久化 + 续打请求 |

> 二者常配合：网络层负责"连上"，应用层负责"从哪续、刷新后还能显示"。

### 2. 断点续打的实现

核心：**定位断点 → 续打请求 → 拼接去重**。

#### 定位断点

| 定位方式 | 说明 |
| --- | --- |
| resume token | 上游 LLM 返回的续传标识（如 Anthropic 的 continuation），续打带上即可从断点继续 |
| Last-Event-ID | SSE 标准字段，重连时带 `Last-Event-ID` 头，服务端从该事件后续传 |
| offset / 已输出字数 | 记录已输出字符数或 token 数，续打时告知服务端从该位置继续 |
| 业务层生成 ID | 每段内容带自增 event id，续打按 id 去重 |

#### 续打请求

客户端把断点标识带回服务端，服务端从断点继续生成流式输出：

```
POST /chat/stream  { conversation_id, resume_from: <last_event_id>, ... }
→ 服务端从 last_event_id 之后继续输出
```

#### 拼接去重

客户端拼接"已输出内容 + 续打内容"，按 event id 去重，防止断点附近内容重复。

### 3. 页面刷新后的内容恢复

刷新会丢失内存中的流式内容，需持久化 + 恢复：

| 步骤 | 做法 |
| --- | --- |
| 增量持久化 | 流式内容每收到一段就写入 localStorage / IndexedDB / 服务端会话存储 |
| 刷新后读取 | 页面加载时读取持久化的已输出内容，恢复显示 |
| 判断是否可续 | 会话状态为"未完成"则发起续打请求 |
| 续打恢复 | 续打请求从断点继续，拼接显示 |

> 持久化选型：短内容 localStorage 够用；长对话/多端同步用 IndexedDB 或服务端会话存储。

### 4. 实现步骤

| 步骤 | 说明 |
| --- | --- |
| ① 流式内容增量持久化 | 每个 chunk 写入存储，附 event id / offset |
| ② 断点定位 | 记录最后成功接收的 event id / resume token |
| ③ 续打请求 | 带断点标识请求服务端续传 |
| ④ 拼接去重 | 客户端按 event id 去重合并 |
| ⑤ 状态收尾 | 生成完成后标记会话为"已完成"，不再续打 |

### 5. 代码示例

```javascript
// 增量持久化 + 断点续打
const store = {
  load: (convId) => JSON.parse(localStorage.getItem(`stream:${convId}`) || '[]'),
  save: (convId, events) => localStorage.setItem(`stream:${convId}`, JSON.stringify(events)),
};

function streamWithResume(convId, client) {
  const existed = store.load(convId);                 // 读取已持久化内容
  const lastEventId = existed.length ? existed[existed.length - 1].id : null;
  render(existed.map(e => e.text).join(''));          // 恢复显示

  client.stream({
    conversation_id: convId,
    resume_from: lastEventId,                         // 续打断点
    onMessage: (chunk) => {
      existed.push({ id: chunk.id, text: chunk.text });
      store.save(convId, existed);                    // 增量持久化
      render(chunk.text);
    },
    onDone: () => markFinished(convId),
  });
}
```

### 6. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 断点标识要可靠 | 优先用服务端给的 resume token / event id，别只靠字数（字数易漂移） |
| 去重防重复 | 续打边界附近可能重复，按 event id 严格去重 |
| 持久化限容 | 长对话别无限堆 localStorage，超限转 IndexedDB 或服务端 |
| 可续状态判定 | 只有"未完成且可续"的会话才续打，已完成的别误续 |
| 与报错兜底配合 | 报错中断后提供"继续生成"入口，走续打流程（见 [[10.流式推理中LLM模型报错的兜底策略设计]]） |

### 7. 一句话总结

断点续打 = **定位断点（resume token / Last-Event-ID / offset）→ 续打请求 → 拼接去重**；页面刷新恢复 = **流式内容增量持久化（localStorage/IndexedDB/服务端）→ 刷新后读取恢复显示 → 未完成则续打**。它与网络层重连（[[2.流式返回中网络中断重连的上下文恢复方法及防重复、防丢包策略]]）互补：后者管"连上"，本篇管"从哪续、刷新不丢"。
