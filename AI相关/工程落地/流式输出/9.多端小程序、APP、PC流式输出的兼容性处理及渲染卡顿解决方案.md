## 多端小程序、APP、PC 流式输出的兼容性处理及渲染卡顿解决方案

> 流式输出（打字机效果）是 LLM 应用的标配体验，但 PC、APP、小程序三端对流式协议的支持参差不齐，且高频 token 渲染极易卡顿。本篇讲透"协议兼容"与"渲染性能"两端。SSE 与 WebSocket 的选型见 [[1.大模型流式输出中SSE与WebSocket的选型逻辑、优缺点及适用场景结合高并发、跨端兼容]]。

### 1. 多端流式输出的兼容现状

| 端 | EventSource(SSE) | WebSocket | fetch 流式(ReadableStream) | 现状 |
| --- | --- | --- | --- | --- |
| PC 浏览器 | ✅ 原生 | ✅ 原生 | ✅ 原生 | 三种都支持，首选 SSE |
| APP(WebView) | ⚠️ 多数支持，部分 WebView 参差 | ✅ | ⚠️ 部分 WebView 不稳定 | 需能力检测，常降级 WS |
| APP(原生) | ❌ 无 EventSource | ✅ 原生库 | ✅ NSURLSession/OkHttp 流式 | 用 WS 或原生 HTTP 分块 |
| 小程序(微信等) | ❌ 不支持 | ⚠️ 受限（需 wss+合法域名，不能裸读写流） | ⚠️ 部分支持 `enableChunked` | 常用 WS 或分块 HTTP 降级 |

> 小程序是最棘手的一端：没有 EventSource，WebSocket 受域名白名单与 API 限制，通常靠 `wx.connectSocket` 或 `RequestTask.enableChunked` 分块接收降级。

### 2. 兼容方案：能力检测 + 降级链 + 统一抽象层

**降级链**：优先用体验最好的协议，不支持则逐级降级。

```
SSE(EventSource) → WebSocket → 分块 HTTP(fetch ReadableStream / 小程序 chunked) → 轮询
```

**统一抽象层**：屏蔽底层协议差异，业务层只面对统一接口。

| 抽象接口 | 说明 |
| --- | --- |
| `onOpen` | 连接建立 |
| `onMessage(chunk)` | 收到一段流式文本 |
| `onError(err)` | 出错 |
| `onClose()` | 连接关闭 |
| `send(data)` | 上行（多轮场景） |
| `close()` | 主动断开 |

```javascript
// 统一抽象层：按能力检测选择实现
function createStreamClient(url, options) {
  if (typeof EventSource !== 'undefined' && options.preferSSE) {
    return new SSEClient(url, options);        // PC / 支持 SSE 的 WebView
  }
  if (typeof WebSocket !== 'undefined') {
    return new WSStreamClient(url, options);   // 通用降级
  }
  return new ChunkedHTTPClient(url, options);  // 小程序 / 原生分块兜底
}
```

| 端 | 推荐实现 |
| --- | --- |
| PC 浏览器 | SSE（EventSource） |
| APP WebView | 能力检测 → SSE 或 WebSocket |
| APP 原生 | WebSocket 或原生 HTTP 流式 |
| 小程序 | WebSocket（`wx.connectSocket`）或 `enableChunked` 分块 |

### 3. 渲染卡顿的原因

流式每个 token 触发一次更新，高频下主线程被打满：

| 原因 | 表现 |
| --- | --- |
| 高频打字机渲染 | 每 token 一次 DOM 更新，远超 60fps，掉帧 |
| 虚拟 DOM 重渲染 | 框架对整棵子树 diff，token 越多越慢 |
| 长文本累积 | DOM 节点持续增长，重排重绘成本飙升 |
| Markdown 实时解析 | 每来一个 token 重解析整段，CPU 飙升 |
| 主线程阻塞 | 解析+渲染抢占，输入框/按钮卡死 |

### 4. 渲染卡顿解决方案

| 方案 | 做法 | 收益 |
| --- | --- | --- |
| requestAnimationFrame 节流 | 一帧内的多个 token 合并为一次渲染 | 控制到 60fps，核心手段 |
| 增量 DOM 更新 | 只 append 新文本节点，不重渲染整段 | 避免全量 diff |
| DocumentFragment | 批量插入，减少重排次数 | 降低布局开销 |
| 虚拟列表 | 长对话只渲染可视区消息 | 节点数恒定 |
| 防抖/节流 | 高频更新合并 | 平滑渲染 |
| CSS containment | `contain: content` 隔离重排范围 | 限制重排区域 |
| Markdown 延迟解析 | 流式时纯文本追加，结束后再解析渲染 | 流式阶段零解析开销 |

> 经验：**流式阶段用纯文本追加 + rAF 节流，生成结束再一次性 Markdown 渲染**，是性价比最高的组合。

### 5. 代码示例：rAF 节流打字机渲染

```javascript
class StreamingRenderer {
  constructor(el) {
    this.el = el;
    this.buffer = '';        // 待渲染缓冲
    this.scheduled = false;  // 是否已调度
  }
  push(chunk) {
    this.buffer += chunk;
    if (!this.scheduled) {
      this.scheduled = true;
      requestAnimationFrame(() => this.flush());
    }
  }
  flush() {
    this.scheduled = false;
    if (this.buffer) {
      this.el.appendChild(document.createTextNode(this.buffer));
      this.buffer = '';
      this.el.scrollTop = this.el.scrollHeight;  // 自动滚动到底
    }
  }
}

// 使用：流式 chunk 到达时只调 push，rAF 自动合并渲染
streamClient.onMessage(chunk => renderer.push(chunk));
```

### 6. 多端兼容要点速览

| 要点 | 说明 |
| --- | --- |
| 能力检测优先 | 别假设某端支持某协议，运行时检测再选实现 |
| 降级链兜底 | SSE→WS→分块 HTTP→轮询，保证最差也能用 |
| 统一抽象层 | 业务层不感知协议，便于维护与扩展 |
| 小程序特殊处理 | 域名白名单、`enableChunked`、WS 限制要单独适配 |
| 渲染节流 | rAF 合并是性能命脉，别每 token 直更 DOM |
| 延迟 Markdown | 流式纯文本、结束再解析，省 CPU |

### 7. 一句话总结

多端流式兼容 = **能力检测 + 降级链（SSE→WebSocket→分块 HTTP→轮询）+ 统一抽象层**屏蔽端差异；渲染卡顿 = **rAF 节流合并 + 增量 DOM + 虚拟列表 + 延迟 Markdown**，流式阶段纯文本追加、结束再解析。前端延迟优化的更多策略见场景架构问题目录的《11.大模型API响应延迟超1秒时的前端优化策略》。
