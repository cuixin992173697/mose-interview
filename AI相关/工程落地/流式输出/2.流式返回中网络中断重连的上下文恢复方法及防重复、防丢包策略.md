## 流式返回中网络中断重连的上下文恢复方法及防重复、防丢包策略

### 1. 中断场景与问题

流式输出过程中连接可能因以下原因断开，重连后要保证"接得上、不重复、不丢字"：

| 中断原因 | 说明 |
| --- | --- |
| 网络抖动 | 移动端切换网络、弱网导致连接断 |
| 服务重启/发布 | 推理服务或网关滚动更新 |
| 超时断开 | 网关/CDN 空闲超时主动断 |
| 客户端刷新 | 页面刷新导致连接重建 |

重连的核心矛盾：**已推送给客户端的 token 不能再推（防重复），未推完的不能丢（防丢包）**。

### 2. 上下文恢复方法

| 方法 | 机制 | 适用 |
| --- | --- | --- |
| SSE Last-Event-ID | 浏览器自动重连时带上最后收到的 event id，服务端从该 id 之后续推 | SSE 原生，最省事 |
| 自定义 resume token | 客户端记录进度 token，重连时带回，服务端据此续推 | 非 SSE 或需更强语义 |
| 断点续传 offset | 每个 chunk 带单调序号 offset，重连从 offset+1 续推 | 通用，自定义协议 |

**服务端必备：event 缓冲**。服务端需为每个流保留一段近期已发送 event 的环形缓冲（如最近 N 条或 T 秒），重连时从 Last-Event-ID/resume token 之后回放缓冲里未确认的部分，保证接续。

```
重连流程：
客户端 → 带 Last-Event-ID=120 重连
服务端 → 查缓冲：120 之后有 121~135 未确认
       → 先回放 121~135，再继续推新生成的 136…
```

### 3. 防重复策略

| 策略 | 说明 |
| --- | --- |
| 单调递增 event id | 每个 event 带全局/会话内单调递增 id |
| 客户端去重 | 收到 id ≤ 已处理最大 id 的 event 直接丢弃 |
| 幂等拼接 | 客户端按 id 去重后再追加到消息文本，避免重连回放导致重复字 |

> 关键：去重在客户端做最可靠，因为服务端不知道客户端到底收到哪条了（除非有 ack）。

### 4. 防丢包策略

| 策略 | 说明 |
| --- | --- |
| 序列号 + ack | 每个 event 带序号，客户端定期 ack 最大连续序号，服务端据此清理缓冲 |
| 缺失检测 | 客户端发现序号跳变（如 120 后直接 123）→ 标记缺失 121~122，请求重传或重连 |
| 缓冲兜底 | 服务端缓冲未 ack 的 event，重连时回放，覆盖丢包 |
| 超时收尾 | 流结束后发结束标志（`event: done`），客户端未收到则判定丢包，触发整体重取 |

### 5. 实现要点

| 要点 | 说明 |
| --- | --- |
| 缓冲容量 | 按"最大重连窗口时间 × 生成速率"估，过大占内存，过小重连接不上 |
| id 单调性 | 多实例/多分片下需全局单调（如雪花算法或会话内递增） |
| 续推边界 | 服务端续推要从"已确认 id 之后"开始，而非"已生成之后"，否则丢中间段 |
| 生成已完成的重连 | 流已结束但客户端断了：重连时服务端发现已结束，直接回放缓冲剩余 + done 标志 |
| 会话标识 | 重连要带会话 id + 流 id，服务端据此定位缓冲 |

### 6. 一句话总结

流式重连靠 **event 单调 id + 服务端缓冲回放** 实现上下文恢复：重连带 `Last-Event-ID`/resume token 续推，客户端按 id 去重防重复、按序号+ack+缺失检测防丢包，服务端保留未 ack 的 event 缓冲兜底。断点续打与刷新恢复见 [[11.流式输出断点续打的实现及页面刷新后的内容恢复方法]]，多轮有序性见 [[5.多轮对话+流式输出的消息有序性、上下文完整性保障及跨服务流式透传实现]]。
