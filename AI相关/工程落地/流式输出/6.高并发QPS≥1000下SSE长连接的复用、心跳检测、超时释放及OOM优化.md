## 高并发 QPS≥1000 下 SSE 长连接的复用、心跳检测、超时释放及 OOM 优化

SSE 是"一请求一长连接"。QPS≥1000 意味着同时挂着上千条长连接，每条都占 fd/内存/线程，稍有不慎就 OOM 或 fd 耗尽。本篇讲怎么撑住千级并发长连接。

### 1. 高并发下的挑战

| 资源 | 千级连接的影响 | 风险 |
| --- | --- | --- |
| 文件描述符 fd | 每连接 1 fd，1000+ 连接 | fd 耗尽（ulimit），新连接被拒 |
| 内存 | 每连接 buffer + 上下文 | 积压即 OOM |
| 线程 | 同步阻塞模型每连接 1 线程 | 线程爆炸 / 上下文切换开销 |
| 上游 LLM | 千级并发推理请求 | 上游限流 / 排队 / 成本飙升 |

### 2. 连接复用

SSE 协议本身是"一请求一响应流"，不像 WebSocket 可双向复用。工程上的"复用"指：

| 复用手段 | 说明 |
| --- | --- |
| 会话绑定连接 | 同一 session_id 复用同一条 SSE 连接，避免重复建连 |
| 连接池（上游） | 业务→推理服务侧用连接池复用 HTTP 连接，减少握手开销 |
| 多路复用（HTTP/2） | 上游用 HTTP/2 多路复用，一条 TCP 跑多个 stream |
| 限制单用户连接数 | 同一用户同时只允许 1 条流，避免刷接口占连接 |

### 3. 心跳检测

长连接可能因中间网关/NAT 静默断开而"假活"，需心跳保活与探活：

| 心跳做法 | 说明 |
| --- | --- |
| SSE 注释保活 | 定期发 `: ping\n\n`（SSE 注释行），客户端无感但保持 TCP 活跃 |
| 应用层 ping | 定期发 `event: ping` 数据帧，客户端可回 pong 探活 |
| 间隔 | 通常 15~30s 一次，太频浪费带宽，太慢探测不到断连 |
| 死连接判定 | 连续 N 次 ping 无响应（或写失败）判定死连接，主动关闭释放 |

```text
: ping              ← SSE 注释，保持连接，前端 EventSource 自动忽略

event: ping
data: {"ts":1700000000}   ← 应用层心跳，前端可回 pong
```

### 4. 超时释放

防止僵尸连接长期占资源：

| 超时类型 | 触发 | 动作 |
| --- | --- | --- |
| 首 token 超时 | 建连后 N 秒无任何数据 | 关闭连接，返回超时错误 |
| 空闲超时 | 流结束后或长时间无数据 | 关闭连接释放资源 |
| 总时长超时 | 单条流最长存活时间 | 强制关闭防泄漏 |
| 心跳超时 | N 次心跳无响应 | 判死连接，关闭 |

### 5. OOM 优化

千级连接下 OOM 是头号风险，核心原则"流式不积压、buffer 有上限"：

| 优化项 | 说明 |
| --- | --- |
| 流式不积压 | 收到 chunk 立即转发/写出，不在内存攒全量 |
| 每连接 buffer 上限 | 单连接缓冲区设上限（如 64KB），超限触发背压或丢弃 |
| 背压 | 下游慢时暂停上游读取，而非无限缓存 |
| 异步非阻塞 | 用 reactor/epoll/Netty/Node 异步模型，1 线程处理多连接，避免每连接 1 线程 |
| 连接数上限 | 设全局连接数上限，超限拒绝新连接（限流保护） |
| 及时释放 | 流结束/异常/客户端断开立即释放连接与上游资源 |
| 上下文外置 | 会话上下文存 Redis，不在连接内存里持有大历史 |

### 6. 容量估算

| 维度 | 估算 |
| --- | --- |
| fd | 1000 连接 ≈ 1000 fd，需调高 ulimit（如 65535） |
| 内存 | 每连接 buffer + 元数据 ≈ 几十 KB~百 KB，1000 连接 ≈ 几十~百 MB |
| 线程 | 异步模型下线程数固定（如 CPU×2），与连接数解耦 |
| 上游 | 1000 并发推理需上游能扛，否则排队/限流 |

### 7. 一句话总结

千级 SSE 长连接要靠"异步非阻塞模型（1 线程多连接）+ 流式不积压 + 每连接 buffer 上限 + 背压 + 心跳探活 + 多级超时释放 + 连接数限流"撑住，核心是防 OOM 与 fd 耗尽；选型对比见 [[1.大模型流式输出中SSE与WebSocket的选型逻辑、优缺点及适用场景结合高并发、跨端兼容]]。
