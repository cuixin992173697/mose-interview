## 动态知识更新场景下 RAG 的增量更新机制设计：避免全量向量化

> 知识频繁变更（文档改了/删了/新增），全量重建向量库成本高、延迟大。本篇讲增量更新机制。向量库增量更新的通用实现见 rag 目录的《45.RAG中向量数据库增量更新的实现方式》。

### 1. 动态更新需求与全量重建的痛点

| 痛点 | 说明 |
| --- | --- |
| 全量重建成本高 | 每次变更都把全库重新 embedding + 建索引，百万级文档要数小时+大量算力 |
| 更新延迟大 | 全量重建期间检索结果是旧的，知识时效性差 |
| 服务中断 | 全量重建/切换索引可能影响在线检索 |
| 浪费 | 大部分文档没变，重新 embedding 是无效算力 |

> 目标：**只对变更部分重新 embedding + upsert，未变的不动**，做到准实时、低成本。

### 2. 增量更新机制

| 环节 | 做法 |
| --- | --- |
| 变更检测 diff | 对比文档新版本与旧版本（内容哈希/版本号/更新时间），识别哪些文档/切片变了 |
| 增量 embedding | 仅对变更的 chunk 重新调用 embedding 模型，未变的复用旧向量 |
| 增量入库 upsert | 变更 chunk 的向量 upsert 进向量库（覆盖旧向量）；新增 chunk 插入；删除 chunk 移除 |
| CDC 变更捕获 | 接文档源的变更事件（数据库 CDC / 文件监听 / 业务事件），触发增量管道 |
| 版本化 | 文档/切片带版本号，向量库支持按版本查询/回滚 |

### 3. 避免全量向量化的关键

| 要点 | 说明 |
| --- | --- |
| 切片级 diff | 文档变更不一定整篇变，按 chunk 级别 diff，只重算变化的 chunk |
| 向量复用 | 未变 chunk 的向量直接保留，不重新 embedding |
| 增量索引 | HNSW 支持在线插入/upsert，无需重建索引；IVF 需分区或定期重建 |
| 软删除+合并 | 删除用标记（墓碑），后台低峰期合并清理，避免频繁物理删除 |

```
文档变更事件 → 切片级 diff → 识别变更 chunk → 仅变更 chunk 重新 embedding → upsert 向量库 → 删除旧版本 → 检索立即可用
```

### 4. 一致性与旧数据清理

| 问题 | 方案 |
| --- | --- |
| 检索到旧版本 | upsert 原子覆盖 + 检索带版本过滤（只查最新版本） |
| 删除未生效 | 软删除标记 + 检索过滤已删除 + 后台 compaction 物理清理 |
| 增量与全量不一致 | 定期（如每天低峰）跑一次全量校对/重建修正漂移 |
| 索引膨胀 | 墓碑/旧版本累积，定期合并清理 |

### 5. 一句话总结

动态知识增量更新 = **切片级 diff 检测变更 → 仅变更 chunk 重新 embedding → upsert 覆盖向量库（HNSW 在线更新）→ 软删除+版本过滤保证检索一致性 → 定期全量校对修正漂移**，避免全量向量化，做到准实时低成本更新。一致性保障见 [[2.文档频繁更新与删除场景下向量库的实时一致性保障及旧数据、脏数据规避]]，检索滞后同步见 [[18.RAG检索滞后问题的解决方法（文档更新后检索结果及时同步）]]。
