## 文档频繁更新/删除场景下向量库的实时一致性保障及旧数据、脏数据规避

> 知识库频繁增删改时，向量库容易出现"删了还能搜到、改了搜到旧版、新旧并存"的脏数据问题。本篇讲一致性保障与脏数据规避。

### 1. 一致性问题从哪来

| 问题 | 表现 | 根因 |
| --- | --- | --- |
| 删除未生效 | 文档已删，检索仍返回 | 硬删除延迟、软删除未过滤、索引未 compaction |
| 旧版本残留 | 文档已更新，检索返回旧内容 | upsert 未覆盖、旧向量未删 |
| 新旧并存 | 同一文档新旧两份都召回 | 更新=删旧+插新之间有时间窗 |
| 检索到脏数据 | 返回半残/错误/重复片段 | 写入未校验、去重缺失、并发写冲突 |
| 索引与库不一致 | 向量库有但元数据没有（或反之） | 双写非原子、部分失败 |

### 2. 一致性保障机制

#### upsert 原子性

更新文档时用 upsert（按主键覆盖），而非"删后插"，避免中间空窗：

| 方式 | 问题 | 推荐 |
| --- | --- | --- |
| 先删后插 | 删与插之间有检索空窗，可能搜不到 | 不推荐 |
| upsert 覆盖 | 原子覆盖同主键，无空窗 | 推荐 |
| 版本化插入 | 新版本插入 + 旧版本标记过期 | 适合需灰度的场景 |

> 用文档 id 作为主键，upsert 时同 id 覆盖，保证一文档一向量。

#### 软删除 + compaction

| 机制 | 说明 |
| --- | --- |
| 软删除 | 删除时打 tombstone 标记，检索时过滤，立即对查询不可见 |
| compaction | 后台定期物理清理被标记的向量，回收空间 |
| 优点 | 删除即时生效（查询层过滤），物理清理异步不阻塞 |

> Milvus 的 delete 是软删除（标记），compaction 物理清理；查询时自动排除已删向量。

#### 版本号与写后读一致性

| 机制 | 说明 |
| --- | --- |
| 文档版本号 | 每次更新递增 version，向量带 version 元数据，检索取最新 version |
| 写后读一致性 | 写入后等索引刷新/刷新间隔内不返回旧数据 |
| 一致性级别 | strong（即时一致）/ bounded staleness（有界延迟）/ eventual（最终一致），按场景选 |

### 3. 旧数据规避

| 手段 | 说明 |
| --- | --- |
| 版本化 | 同 id 只保留最新 version，旧 version 标记过期 |
| 过期标记 + 过滤 | 检索时 filter 掉 expired=true / version<current |
| compaction 定期清理 | 后台清理过期/已删向量，防累积 |
| 双写校验 | 更新后回查确认新版本可检索、旧版本不可见 |

### 4. 脏数据规避

| 手段 | 说明 |
| --- | --- |
| 写入校验 | 入库前校验向量维度/元数据完整性/内容非空 |
| 去重 | 文档级哈希去重 + 近重复去重，防重复入库 |
| 一致性巡检 | 定期比对"源文档库 vs 向量库"，发现孤儿/缺失 |
| 并发写控制 | 同文档并发更新用锁/版本号 CAS，防覆盖丢失 |
| 失败补偿 | 写入部分失败时重试或回滚，保证双写（向量库+元数据）一致 |

### 5. 更新/删除的标准流程

```
更新文档：
  ① 源文档库更新（version+1）
  ② 重新切片 + embedding
  ③ 向量库 upsert（id 不变，version+1，覆盖旧向量）
  ④ 失效相关缓存（见 [[3.同一用户同一问题的检索结果缓存设计及缓存过期与新知识更新的平衡]]）
  ⑤ 回查确认新 version 可检索

删除文档：
  ① 源文档库标记删除
  ② 向量库软删除（tombstone，查询立即过滤）
  ③ 失效相关缓存
  ④ compaction 阶段物理清理
```

### 6. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 主键设计 | 文档 id 做主键，upsert 覆盖而非删插 |
| 检索带 version 过滤 | 关键场景检索时 filter version=max，兜底防旧 |
| 监控一致性 | 定期巡检源库 vs 向量库数量差，告警不一致 |
| 控制最终一致窗口 | 设刷新间隔上限，避免长时间新旧并存 |
| 缓存联动 | 更新/删除必须联动失效缓存，否则搜到旧缓存 |

> 增量更新机制（避免全量重建）见 [[14.动态知识更新场景下RAG的增量更新机制设计避免全量向量化]]，更新后检索及时同步见 [[18.RAG检索滞后问题的解决方法（文档更新后检索结果及时同步）]]，向量库增量更新通用方法见 rag 目录的《45.RAG中向量数据库增量更新的实现方式》。

### 7. 一句话总结

频繁增删改下保障一致性 = **upsert 原子覆盖（主键 id 不变）+ 软删除即时过滤 + 版本号防旧 + compaction 定期清理 + 写入校验去重巡检防脏**，关键是避免"删插空窗"和"新旧并存"，并联动缓存失效防止搜到旧结果。
