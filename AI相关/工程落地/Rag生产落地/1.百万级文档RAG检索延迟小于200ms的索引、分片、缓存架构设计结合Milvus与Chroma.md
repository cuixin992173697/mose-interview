## 百万级文档 RAG 检索延迟 <200ms 的索引、分片、缓存架构设计（结合 Milvus/Chroma）

> 目标：百万级向量规模下，端到端检索（query→embedding→ANN→返回 top-K）延迟压到 200ms 以内。核心三板斧：**索引调参 + 分片并行 + 多级缓存**。

### 1. 延迟从哪来（先定位瓶颈）

| 环节 | 典型耗时 | 优化手段 |
| --- | --- | --- |
| query embedding | 10~30ms | 小模型 + 缓存 |
| ANN 向量检索 | 20~100ms | 索引调参 + 分片并行 |
| 元数据过滤 | 5~30ms | 标量索引 + pre-filter |
| 结果合并/序列化 | 5~15ms | 精简字段 |
| 网络往返 | 10~30ms | 就近部署 + 连接池 |

200ms 预算分配参考：embedding ≤30ms + 检索 ≤100ms + 过滤合并 ≤40ms + 网络 ≤30ms。

### 2. 索引优化（检索本身要快）

#### HNSW（图索引，精度高速度快，内存大）

| 参数 | 作用 | 调参建议 |
| --- | --- | --- |
| M | 每节点连接数 | 16~32，越大精度越高、内存越大 |
| efConstruction | 建图候选数 | 200~400，影响建图质量 |
| efSearch | 查询候选数 | 50~200，**延迟-精度的主旋钮**，线上可动态调 |

> efSearch 是线上调延迟最直接的参数：降 efSearch 提速但降精度，需用 recall@k 评测找拐点。

#### IVF（聚类倒排，内存省，需训练）

| 参数 | 作用 | 调参建议 |
| --- | --- | --- |
| nlist | 聚类中心数 | 百万级取 √N 量级，如 4096~16384 |
| nprobe | 查询探查簇数 | 8~64，**延迟-精度旋钮**，越大越准越慢 |

| 索引 | 精度 | 速度 | 内存 | 是否需训练 | 适合 |
| --- | --- | --- | --- | --- | --- |
| HNSW | 高 | 快 | 大 | 否 | 百万级、低延迟首选 |
| IVF_FLAT | 中 | 中 | 中 | 是 | 内存敏感 |
| IVF_PQ | 中低 | 快 | 小 | 是 | 超大规模、可牺牲精度 |

> 索引原理与 HNSW/IVF 差异见 rag 目录的《36.向量索引的构建使用方法及HNSW与IVF的差异》《20.向量数据库中HNSW、LSH、PQ的含义》。

### 3. 分片与并行检索

百万级单机可扛，但为低延迟 + 可扩展，生产通常分片：

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 按量分片 | 文档均匀切到 N 个分片，并行检索后合并 top-K | 通用，负载均衡 |
| 一致性哈希 | 按文档 id 哈希分片，增删分片迁移少 | 动态扩缩容 |
| 按业务分片 | 按租户/类目分片，查询只命中相关分片 | 多租户、强隔离 |

```
query → embedding
   ├── 分片1 ANN(top-K) ─┐
   ├── 分片2 ANN(top-K) ─┤→ 合并去重 → 全局 top-K
   └── 分片N ANN(top-K) ─┘
```

并行检索把单分片延迟从 100ms 降到 N 分片并行后的 ~100ms（受最慢分片限制），关键是**每分片 top-K 再全局合并**，别每分片只返回太少。

### 4. 多级缓存（最有效的降延迟手段）

| 缓存层 | key | 价值 | 失效 |
| --- | --- | --- | --- |
| embedding 缓存 | query 文本 hash | 省掉 10~30ms embedding | query 变则失效 |
| 结果缓存（精确） | 归一化 query | 省掉整条检索，<5ms 返回 | TTL / 知识更新 |
| 语义缓存 | query 向量近邻 | 相似问题复用结果 | 难失效，需谨慎 |
| 检索片段缓存 | (query, doc_id) | 省片段二次取 | 文档更新 |

> 语义缓存命中率高时收益巨大，但"相似 query 复用结果"可能返回过时答案，需结合知识版本号失效，详见 [[3.同一用户同一问题的检索结果缓存设计及缓存过期与新知识更新的平衡]]。

### 5. Milvus vs Chroma 选型与配置

| 维度 | Milvus | Chroma |
| --- | --- | --- |
| 定位 | 分布式向量库，大规模生产 | 轻量嵌入式，开发/小规模 |
| 百万级+ | 原生支持，分片/分布式 | 单机可扛百万，再大吃力 |
| 索引 | HNSW/IVF/DiskANN 全支持 | HNSW 为主 |
| 部署 | 集群（多组件） | 单进程/嵌入式 |
| 延迟控制 | 分片并行 + 调参 | 调 ef 即可 |

> 选型详见 rag 目录的《35.RAG项目中Milvus、Pinecone、Chroma向量数据库的选型思路》。**百万级低延迟生产首选 Milvus（分布式分片并行）；中小规模或原型用 Chroma（调 HNSW efSearch）**。

### 6. 整体架构

```
                ┌─ embedding 缓存 ─┐
query ──────────┤                  ├─ embedding ─┐
                └─ (未命中) ───────┘             │
                                                 ▼
        ┌─ 结果缓存(精确) ─┐  命中 → 直接返回 (<5ms)
        └─ (未命中) ───────┘
                                                 │
        ┌──────────┬──────────┬──────────┐       │
        ▼          ▼          ▼          ▼       │
     分片1       分片2       分片3     分片N      │
     HNSW        HNSW        HNSW      HNSW      │
     efSearch    efSearch    efSearch   efSearch  │
        └──────────┴──────────┴──────────┘       │
                      │                          │
                  合并 top-K ─────────────────────┘
                      │
                  元数据过滤 → 返回
```

### 7. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| efSearch/nprobe 动态调 | 按负载动态降参数保延迟，闲时调高保精度 |
| 标量字段建索引 | 元数据过滤走标量索引，否则全表扫拖慢 |
| 连接池 + 就近部署 | 检索服务与向量库同机房，降网络往返 |
| 缓存命中率监控 | 命中率是延迟的核心指标，低则补缓存 |
| 评测保精度 | 调参后必跑 recall@k，别为延迟牺牲到不可用 |
| 分片均衡 | 监控各分片数据量/延迟，防热点 |

> 高并发下的负载均衡与水平扩展见 [[16.高并发下RAG服务的负载均衡及水平扩展设计]]，通用并发调度见 Agent生产落地目录的《7.高并发场景下Agent任务的排队、限流、优先级调度实现》。

### 8. 一句话总结

百万级 <200ms 的核心是 **索引调参（HNSW efSearch / IVF nprobe 平衡精度-速度）+ 分片并行检索（每分片 top-K 再全局合并）+ 多级缓存（embedding/结果/语义缓存）**，大规模用 Milvus 分布式分片、中小规模用 Chroma 调 HNSW，全程用 recall@k 评测保住精度底线。
