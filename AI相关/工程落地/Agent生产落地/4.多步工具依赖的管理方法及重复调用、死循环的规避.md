## 多步工具依赖的管理方法及重复调用、死循环的规避

> Agent 常需多步工具协作（工具 A 的结果喂给工具 B），处理不当就重复调用、死循环。死循环基础解法见 agent 目录的《17.Agent死循环问题的解决方法》。

### 1. 多步工具依赖管理

工具间存在依赖（A 的输出是 B 的输入），需有序编排与状态传递：

| 管理方法 | 说明 |
| --- | --- |
| DAG 编排 | 把工具调用组织成有向无环图，按拓扑序执行，并行无依赖步骤 |
| 状态传递 | 工具 A 结果存入执行上下文/黑板，工具 B 从中读取 |
| 依赖图显式声明 | 复杂流程用图编排（如 LangGraph）显式声明依赖，避免 LLM 乱序 |
| 中间结果缓存 | A 的结果缓存，B 失败重跑不需重算 A |
| 结果格式约定 | 约定工具输出 schema，下游工具可靠解析 |

```
任务：查订单状态 → 查物流 → 通知用户
  get_order(order_id) → status, tracking_no
       ↓ (tracking_no)
  query_logistics(tracking_no) → logistics_info
       ↓ (logistics_info)
  notify_user(logistics_info) → done
```

> LLM 自主编排依赖时，靠上下文里前一步 Observation 提供下游参数；复杂依赖建议用 LangGraph 状态机显式编排（见 [[10.LangChain与LangGraph的生产选型及LangGraph状态机对复杂业务流程的适配]]）。

### 2. 重复调用规避

| 手段 | 说明 |
| --- | --- |
| 工具结果缓存 | 相同 (工具+参数) 结果缓存，重复请求直接命中 |
| 幂等设计 | 工具本身幂等（重复执行不产生副作用），见 [[12.多用户触发同一Agent任务的幂等设计及重复执行规避]] |
| 调用去重 | 执行前查历史调用记录，已成功的不重调 |
| 参数去重 | 连续相同参数调用视为重复，拦截 |
| LLM 提示约束 | Prompt 约束"已调用过的工具结果见上文，勿重复调用" |

### 3. 死循环规避

| 规避手段 | 说明 |
| --- | --- |
| 最大步数 | 硬上限（如 20 步），超限强制终止 |
| 状态去重 | 记录已访问状态，重复状态判循环 |
| 循环检测 | 检测连续 N 步工具+参数重复，判定死循环 |
| 反思打破 | 检测到循环触发 Reflect，强制换策略（见 [[5.Agent反思机制Reflection的实现及失败学习优化策略]]） |
| 资源预算 | token/时间/调用次数总预算，超限熔断 |
| 失败计数熔断 | 同一工具连续失败超阈值，熔断该工具换方案 |
| 人工兜底 | 反复循环触发人工干预（见 [[14.Agent执行过程的可回放、可打断、可人工干预实现]]） |

### 4. 死循环典型场景与对策

| 场景 | 成因 | 对策 |
| --- | --- | --- |
| 工具反复失败重试 | 失败后 LLM 用相同参数重试 | 失败计数熔断 + 反馈错误让 LLM 改参数 |
| 依赖参数缺失循环 | 等上游结果但上游失败 | 依赖失败即终止该分支或重规划 |
| 目标不可达空转 | 目标超出能力，反复尝试 | 最大步数 + Reflect 判定不可达终止 |
| 状态不更新 | 每步状态不变，模型以为没做 | 状态去重检测 |

### 5. 一句话总结

多步依赖管理 = **DAG 编排 + 状态传递 + 中间结果缓存**；重复调用靠**结果缓存 + 幂等 + 去重**；死循环靠**最大步数 + 状态去重 + 循环检测 + 反思打破 + 资源预算**。环路落地见 [[1.Agent执行环路Plan-Act-Observe-Reflect的生产落地及各环节异常处理]]，Schema 见 [[3.Agent工具调用Schema的设计核心及LLM工具选择、参数传递的准确性保障]]。
