## Agent 短长期记忆的存储结构设计及容量与查询速度的平衡

### 1. 短期记忆 vs 长期记忆：存储定位

Agent 记忆分两层，存储介质与生命周期完全不同：

| 维度 | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 生命周期 | 当前会话内，会话结束即失 | 跨会话持久 |
| 存储介质 | 上下文窗口 / 会话存储 / Redis | 向量库 / 图库 / 键值库 |
| 内容 | 当前对话历史、工具结果、中间状态 | 事件、经验、偏好、事实 |
| 访问方式 | 直接拼接进 Prompt | 按相关性检索后注入 |
| 容量 | 受 Context Window 限制 | 可海量，靠索引检索 |
| 速度 | 极快（已在上下文） | 毫秒级（ANN 检索） |

### 2. 存储结构设计

#### 记忆类型

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| 事件 Event | 发生过的事实 | "用户上周问了退货政策" |
| 经验 Experience | 任务执行的经验 | "用工具 A 查库存比工具 B 快" |
| 偏好 Preference | 用户习惯 | "用户偏好简洁回答" |
| 事实 Fact | 确认的信息 | "用户是 VIP 会员" |

#### 元数据（检索与过滤的关键）

每条记忆带结构化元数据，支撑过滤检索与排序：

```json
{
  "id": "mem_001",
  "type": "experience",
  "content": "查询订单状态用 order_service 比直接 SQL 快",
  "metadata": {
    "timestamp": "2026-11-01T10:00:00",
    "source": "task_123",
    "importance": 0.8,
    "session_id": "sess_456",
    "tags": ["订单", "工具选择"]
  }
}
```

### 3. 容量与查询速度的平衡

长期记忆量大，必须在容量与查询速度间平衡：

| 策略 | 作用 | 说明 |
| --- | --- | --- |
| ANN 索引 | 加速检索 | HNSW/IVF，毫秒级检索百万记忆 |
| 分区 | 缩小搜索空间 | 按用户/时间/类型分区，先过滤再检索 |
| 分层记忆 | 兼顾速度与容量 | 近期原文 + 中期摘要 + 远期索引 |
| 冷热分离 | 省成本 | 热数据内存/SSD，冷数据归档 |
| Top-K 检索 | 控注入量 | 只取最相关 K 条进上下文，不全量 |
| 压缩 | 降存储 | 旧记忆摘要化、向量量化 |
| 遗忘策略 | 控容量 | 低重要性/过期记忆删除或降权 |

### 4. 读写流程

```
写入：事件 → embedding → 存向量库(+元数据)
读取：query → embedding → ANN检索+元数据过滤 → Top-K → 拼进 Prompt
```

| 流程 | 步骤 |
| --- | --- |
| 写入 | 事件发生 → 编码成向量 + 元数据 → 存入向量库 |
| 检索 | 当前 query 向量化 → ANN 检索 + 元数据过滤 → Top-K → 注入上下文 |
| 遗忘 | 定期清理低重要性/过期/重复记忆，控容量 |

### 5. 一句话总结

Agent 记忆存储 = **短期靠上下文/Redis（快但易失），长期靠向量库+元数据（持久可检索）**，通过 ANN 索引、分区、分层记忆、冷热分离、Top-K、压缩、遗忘策略在容量与查询速度间平衡。记忆机制详见 agent 目录的《12.LLM Agent长期记忆能力的实现方法》《22.Agent系统中短期记忆与长期记忆的差异及存储检索方式》，反思写入记忆见 [[5.Agent反思机制Reflection的实现及失败学习优化策略]]。
