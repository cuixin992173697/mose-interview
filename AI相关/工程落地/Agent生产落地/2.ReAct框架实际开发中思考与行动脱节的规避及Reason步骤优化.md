## ReAct 框架实际开发中思考与行动脱节的规避及 Reason 步骤优化

> ReAct 的核心是 Thought(reason) 指导 Action。但实际开发中 LLM 常出现"想一套做一套"的脱节。ReAct 循环基础见 agent 目录的《1.ReAct循环的完整过程》。

### 1. 思考与行动脱节的典型问题

| 脱节问题 | 表现 | 危害 |
| --- | --- | --- |
| Thought 与 Action 不一致 | 想着查数据库，实际调了搜索 API | 执行错工具，任务跑偏 |
| LLM 编造 Action | 输出不存在的工具名/幻觉工具 | 调用失败、报错循环 |
| Reason 空洞无推理 | "我需要查询一下，调用 query 工具" 无实际推理 | 推理链断裂，退化为乱试 |
| Action 参数与 Thought 矛盾 | Thought 说查 2024 年，参数传 2023 | 结果错且难排查 |
| 跳过 Thought 直接 Act | 省略推理直接给工具调用 | 失去 ReAct 优势，错误无法自我修正 |
| Observation 后 Thought 忽略结果 | 不分析 Observation 就盲目下一步 | 重复无效调用、死循环 |

### 2. 脱节规避方法

| 方法 | 说明 |
| --- | --- |
| function calling 强制结构化 | 用 API 原生 tool_use 结构化字段，Thought 与 Action 绑定输出，杜绝文本解析脱节 |
| Reason 约束模板 | 强制 Reason 含三要素：当前状态 + 缺失信息 + 下一步理由，缺一重生成 |
| Action 参数 schema 校验 | 参数类型/枚举/必填校验，与 Thought 矛盾则回退重生成 |
| Thought-Action 一致性检查 | 轻量校验：Action 工具是否在 Reason 提到、参数是否与 Reason 描述一致 |
| 工具白名单 | Action 工具必须命中已注册工具集，否则判失败 |
| Observation 强制引用 | 下轮 Reason 必须引用上轮 Observation，强制闭环 |

### 3. Reason 步骤优化

Reason（Thought）质量直接决定 Agent 质量。优化手段：

| 优化点 | 做法 |
| --- | --- |
| 引导提示模板 | 给 Reason 固定句式："已知 X，还缺 Y，因此下一步做 Z" |
| 避免空洞套话 | 禁用"我觉得""可能"等模糊词，要求具体依据 |
| CoT 约束 | 要求分步推理，先分析再决策 |
| Few-shot 示范 | 给 2-3 个高质量 Reason 示例，规范推理范式 |
| Reason 长度约束 | 太短=没推理，太长=发散，限制合理区间 |
| 失败 Reason 重生成 | 校验不通过则带反馈让 LLM 重写 Reason |

### 4. Prompt 模板示例

```text
你是一个严谨的 ReAct Agent。每轮必须按以下结构输出：

Reason: 【已知】<当前已知信息>；【缺失】<还缺什么>；【下一步】<因此要做什么及理由>
Action: <工具名>
Action Input: <JSON 参数，必须与 Reason 一致>

规则：
1. Action 必须在工具列表内，参数必须与 Reason 的【下一步】一致。
2. Reason 不允许空洞，必须基于上一轮 Observation（首轮除外）。
3. 信息足够时输出 Final Answer，不再调用工具。
```

### 5. 一句话总结

规避 ReAct 脱节 = **用 function calling 绑定 Thought-Action + Reason 强制三要素（已知/缺失/理由）+ Action 参数 schema 校验 + 一致性检查**，并用模板与 Few-shot 优化 Reason 质量，让"想"真正指导"做"。Schema 设计见 [[3.Agent工具调用Schema的设计核心及LLM工具选择、参数传递的准确性保障]]。
