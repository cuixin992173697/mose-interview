## Agent 执行过程的可观测性设计及全链路追踪实现

### 1. 为什么 Agent 特别需要可观测性

Agent 是多步、自主、调用工具、有副作用的系统，比单次 LLM 调用复杂得多：一步出错可能级联失败、工具调用有副作用、成本和延迟难以预测。不可观测 = 不可运维。

| 痛点 | 说明 |
| --- | --- |
| 多步级联 | 一步失败导致后续全错，需定位是哪一步 |
| 工具副作用 | 调了什么工具、传什么参数、改了什么数据 |
| 成本不可控 | token/步数/耗时易超预算 |
| 非确定性 | 同一输入可能走不同路径，需追踪实际执行链 |
| 故障难复现 | 需回放当时状态 |

### 2. 可观测性三支柱落地

| 支柱 | Agent 场景落地 |
| --- | --- |
| 日志 Logging | 每步 Thought/Action/Observation 结构化日志 |
| 指标 Metrics | 错误率/延迟/成功率/步数/token/成本 |
| 追踪 Tracing | traceId 贯穿全链路、span 串联各环节 |

### 3. 执行过程可观测（每步埋点）

在 Agent 执行环路每个关键点埋点：

| 环节 | 埋点内容 |
| --- | --- |
| Plan/Thought | 推理内容、决策的工具、参数 |
| Action | 工具名、参数、调用 ID |
| Observation | 工具返回、耗时、状态(成功/失败) |
| Reflect | 反思结论、是否修正 |
| 终止 | 终止原因、总步数、总 token、总耗时 |

结构化日志示例：

```json
{"trace_id":"t1","span_id":"s3","step":3,"event":"action","tool":"search","params":{"q":"RAG"},"status":"ok","duration_ms":120,"tokens":50}
```

### 4. 全链路追踪

| 要素 | 说明 |
| --- | --- |
| traceId | 一次 Agent 任务一个，贯穿网关→业务→Agent→工具→上游 LLM |
| span | 每个环节一个 span（LLM 调用/工具调用/检索），父子串联 |
| event 级追踪 | 每步 Thought/Action/Observation 作为 span 内 event |
| OpenTelemetry | 用 OTel 标准适配，对接 Jaeger/Tempo 等 |
| 跨服务透传 | traceId 随请求头逐跳传递 |

跨服务流式透传的日志埋点与全链路追踪见流式输出目录的《12.跨服务流式透传的日志埋点设计及全链路追踪实现》。Hook 中间件是实现埋点的理想挂载点，见 agent 目录的《39.Agent系统中Hook中间件的作用、典型场景及OpenClaw的Hook系统设计》。

### 5. 监控告警指标

| 指标 | 说明 | 告警阈值示例 |
| --- | --- | --- |
| 成功率 | 任务成功完成比例 | <90% |
| 错误率 | 失败比例 | >10% |
| 步数 | 平均/最大执行步数 | 单任务 >20 步 |
| 延迟 | P50/P95/P99 端到端耗时 | P95 >30s |
| token 消耗 | 单任务/聚合 token | 超预算 |
| 成本 | 单任务 LLM+工具成本 | 超阈值 |
| 工具失败率 | 各工具调用失败比例 | >5% |
| 死循环率 | 触发 max_steps 终止比例 | >1% |

### 6. 一句话总结

Agent 可观测性 = 三支柱（结构化日志 + 指标 + 追踪）落地到执行环路每步埋点，用 traceId/span 贯穿全链路（OpenTelemetry 适配），监控成功率/错误率/步数/延迟/成本告警；它是 Agent 可运维、可定位、可优化的基础，评估指标见 [[18.Agent任务完成率的评估方法及生产中的核心统计指标成功率、错误率等]]，回放与干预见 [[14.Agent执行过程的可回放、可打断、可人工干预实现]]。
