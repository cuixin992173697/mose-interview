## 多 Agent 协作的适用场景及 OpenClaw 对子 Agent 的支持方式

### 1. 为什么需要多 Agent

单 Agent 在复杂任务下有局限：上下文易爆、单一角色能力有限、工具集过大降低决策准确率、难以并行。多 Agent 协作把任务拆给多个专职 Agent 各司其职。

### 2. 适用场景

| 场景 | 说明 | 例子 |
| --- | --- | --- |
| 复杂任务拆分 | 大任务拆成子任务分别攻克 | 软件工程：规划→编码→测试→评审 |
| 专业分工 | 不同 Agent 擅长不同领域/工具 | 检索 Agent + 计算 Agent + 写作 Agent |
| 并行加速 | 互不依赖的子任务并行执行 | 多源数据同时检索 |
| 讨论辩论 | 多视角辩论提升决策质量 | 正方/反方/裁判 Agent |

### 3. 协作模式

| 模式 | 结构 | 特点 |
| --- | --- | --- |
| 层级 Supervisor | 一个父 Agent 统筹，派子 Agent 执行 | 控制清晰，最常用 |
| 并行 | 多 Agent 同时执行互不依赖任务 | 快，需结果合并 |
| 协作 | 多 Agent 共享状态协同推进 | 紧耦合，需通信 |
| 辩论 Debate | 多 Agent 针锋相对，裁判裁决 | 提升决策鲁棒性 |

### 4. OpenClaw 对子 Agent 的支持

OpenClaw 这类 Agent 框架的典型设计，支持父 Agent 派生子 Agent 形成层级协作：

```
父 Agent（Supervisor）
   │  拆解任务 + 派生
   ├─→ 子 Agent A（独立 Context + Runner + 工具集）→ 结果回传
   ├─→ 子 Agent B（独立 Context + Runner + 工具集）→ 结果回传
   └─→ 父 Agent 汇总 → 输出
```

| 支持要点 | 说明 |
| --- | --- |
| 派生 | 父 Agent 按子任务生成子 Agent，指定其角色/工具/Skills |
| 独立上下文 | 子 Agent 有自己的 Context Engine 与 Runner，与父隔离，避免上下文互相污染 |
| 独立 Runner | 子 Agent 走完整 Thought→Action→Observation 循环（见 [[26.OpenClaw的Agent Runner工作原理及运行阶段]]） |
| 结果回传 | 子 Agent 完成后把结果（含引用）回传父 Agent，父汇总决策 |
| 生命周期管理 | 子 Agent 完成或超时后回收，释放资源 |

### 5. 何时用子 Agent vs 单 Agent

| 维度 | 单 Agent | 多 Agent / 子 Agent |
| --- | --- | --- |
| 任务复杂度 | 简单线性 | 多阶段/多领域 |
| 上下文压力 | 低 | 高（需隔离） |
| 并行需求 | 无 | 有 |
| 控制复杂度 | 低 | 高（需协调） |

> 子 Agent 边界与限制见 [[41.父Agent生成子Agent的边界问题及OpenClaw的限制保护措施]]，多 Agent 通信协调见 [[42.多Agent间的通信协调方式及OpenClaw中Gateway的作用]]，Agent 基本架构见 [[9.LLM Agent的基本架构组成]]。

### 6. 一句话总结

多 Agent 协作适用于复杂任务拆分、专业分工、并行加速与辩论决策；OpenClaw 这类框架支持父 Agent 派生子 Agent——子 Agent 拥有独立上下文与 Runner、结果回传父 Agent 汇总、生命周期受管理——以层级 Supervisor 模式实现可控的多 Agent 协作。
