## 长对话裁剪无效时的处理方法及 OpenClaw 的 Compaction 策略

### 1. 什么时候"裁剪"会失效

最简单的长对话处理是**截断**——丢掉最早的消息只留最近 N 轮。但很多场景下裁剪会失效：

| 失效场景 | 说明 |
| --- | --- |
| 关键信息分散各处 | 早期某轮的关键事实，后续一直依赖，截断后"失忆" |
| 整段都有用 | 近期对话本身就很长，截断哪段都丢信息 |
| 决策/约定需贯穿全程 | 开头定下的规则/目标，中间不能忘 |
| 工具结果需回溯 | 之前工具查到的数据，后面还要引用 |
| 简单截断破坏上下文连贯 | 丢了中间轮次，模型接不上 |

一句话：**当"该记的"分散在整段对话里时，按时间简单截断必然丢关键事实。**

### 2. 通用处理方法

| 方法 | 思路 |
| --- | --- |
| 摘要合并 | 把旧对话压缩成摘要，保留要点 |
| 分层记忆 | 近期原文 + 中期摘要 + 远期索引 |
| 重要性评分保留 | 给每段打重要性分，低分先丢 |
| 外部化检索 | 旧内容存外部，按需检索召回 |

### 3. OpenClaw 的 Compaction 策略

OpenClaw 这类 Agent 框架的典型设计，对长对话做 **Compaction（结构化压缩）** 而非简单截断。核心区别：截断是"按时间一刀切丢内容"，Compaction 是"把旧内容**转化形态**保留下来"。

```
触发 Compaction（接近 Context Window 阈值时）
   │
   ├─ 旧对话 ──→ 摘要化（压缩成要点，保留语义）
   ├─ 关键事实/决策/工具结果 ──→ 抽取归档（结构化保存，不丢）
   ├─ 近期窗口 ──→ 保留原文（保证当前推理连贯）
   └─ 归档内容 ──→ 外置长期记忆（向量库），按需检索注入
```

| Compaction 动作 | 处理对象 | 产出 |
| --- | --- | --- |
| 摘要化 | 早期多轮对话 | 一段压缩摘要 |
| 抽取归档 | 关键事实/决策/工具结果 | 结构化条目（可检索） |
| 保留原文 | 近期 N 轮 | 原样保留 |
| 外置记忆 | 归档内容 | 存向量库，按需召回 |

### 4. Compaction 触发时机

Compaction 不是每轮都做（成本高），而是**接近窗口阈值时触发**：

| 时机 | 说明 |
| --- | --- |
| 阈值触发 | 上下文 token 占用达到预设阈值（如 70%~80%）时触发 |
| 主动触发 | 检测到即将进行长任务/多工具调用前，提前压缩 |
| 不触发 | 短对话、token 充裕时保持原文，避免无谓压缩损耗 |

> 这与业界已知的 auto-compact/上下文压缩机制一致：平时保留原文保证质量，临近超限时才压缩。

### 5. Compaction vs 简单裁剪

| 维度 | 简单裁剪（截断） | Compaction（结构化压缩） |
| --- | --- | --- |
| 处理方式 | 按时间丢弃 | 转化形态保留 |
| 信息保留 | 差（早期全丢） | 好（摘要+归档+外置） |
| 关键事实 | 易丢失 | 抽取归档不丢 |
| 近期连贯 | 保留 | 保留 |
| 长期可回溯 | 不可 | 外置记忆可检索召回 |
| 成本 | 低 | 较高（需摘要/归档） |

### 6. 一句话总结

当长对话关键信息分散、简单裁剪会丢事实时，OpenClaw 这类框架用 **Compaction 结构化压缩**——旧对话摘要化、关键事实抽取归档、近期原文保留、归档内容外置长期记忆按需检索——替代简单截断，在压缩上下文的同时不丢关键信息。整体长对话方案见 [[27.LLM Context Window上下Agent长对话的实现及OpenClaw的解决方案]]，Context Engine 抽象见 [[30.OpenClaw中Context管理抽象为可插拔Context Engine的原因及支持策略]]，记忆机制见 [[22.Agent系统中短期记忆与长期记忆的差异及存储检索方式]]。
