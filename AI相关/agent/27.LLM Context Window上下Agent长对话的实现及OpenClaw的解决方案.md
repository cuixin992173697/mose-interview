## LLM Context Window 下 Agent 长对话的实现及 OpenClaw 的解决方案

### 1. 问题：长对话为什么会撑爆 Context Window

LLM 有固定的 Context Window（上下文 token 上限，如 8K/32K/128K/200K）。Agent 做长对话时，上下文会持续累积，比单轮问答更容易超限：

| 累积来源 | 说明 |
| --- | --- |
| 多轮对话历史 | 每轮 user/assistant 消息都要带上 |
| 工具调用结果 | 每次工具返回都追加进上下文，可能很长 |
| 记忆注入 | 长期记忆检索回来塞进上下文 |
| System Prompt | 角色定义、工具说明等固定占用 |
| 中间推理 | ReAct 的 Thought/Observation 逐步堆积 |

一旦累积超过 Context Window，轻则**早期信息被截断丢失**（模型"失忆"），重则**直接报错无法调用**。Agent 长对话的核心难题就是：**如何在有限窗口内，让模型始终记得"该记的"，忘掉"可忘的"。**

### 2. 通用实现方式

| 方式 | 思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 截断（Truncation） | 只保留最近 N 轮，丢弃早期 | 简单、快 | 早期关键信息直接丢失 |
| 摘要（Summarization） | 把旧对话压缩成摘要再带上 | 保留要点、省 token | 摘要可能丢细节、有损 |
| 外部长期记忆 | 旧对话存外部（向量库），按需检索注入 | 窗口几乎不限、按需召回 | 多一次检索、依赖检索质量 |
| 滑动窗口 | 固定大小窗口向前滑动 | 平衡近期完整与总量 | 跨窗口信息断裂 |
| 分层记忆 | 近期原文 + 中期摘要 + 远期索引 | 兼顾细节与长期 | 实现复杂 |

### 3. OpenClaw 的解决方案

OpenClaw 这类 Agent 框架的典型设计，不靠单一手段，而是用 **Context Engine + Compaction + 外置长期记忆** 三件套组合管理长对话：

```
长对话上下文
   │
   ├─→ Context Engine：动态管理上下文预算，监控 token 占用
   │        │
   │        ├─ 未超阈值：正常拼接，保留完整上下文
   │        └─ 接近阈值：触发 Compaction
   │
   ├─→ Compaction：结构化压缩（非简单截断）
   │        ├─ 旧对话 → 摘要化
   │        ├─ 关键事实/决策/工具结果 → 抽取归档
   │        └─ 近期窗口 → 保留原文
   │
   └─→ 长期记忆外置：归档内容存向量库
            └─ 后续按需检索注入回上下文
```

| 组件 | 职责 | 解决的问题 |
| --- | --- | --- |
| Context Engine | 监控 token 预算、决定何时压缩、组装上下文 | 主动管理而非被动超限报错 |
| Compaction | 结构化压缩旧上下文（摘要+归档） | 比截断保留更多信息，详见 [[29.长对话裁剪无效时的处理方法及OpenClaw的Compaction策略]] |
| 外置长期记忆 | 归档内容存向量库，按需检索 | 窗口不再受限于对话长度 |

### 4. 方案对比

| 方案 | 信息保留 | 实现复杂度 | 适合对话长度 |
| --- | --- | --- | --- |
| 简单截断 | 差（早期全丢） | 低 | 短 |
| 纯摘要 | 中（有损） | 中 | 中 |
| OpenClaw 组合（Context Engine+Compaction+外置记忆） | 好（结构化保留+按需召回） | 高 | 长/超长 |

### 5. 一句话总结

Agent 长对话的核心是在有限 Context Window 内"记得该记的"——OpenClaw 这类框架用 **Context Engine 动态管理预算 + Compaction 结构化压缩 + 外置长期记忆按需检索** 三件套，替代简单截断，让超长对话既不报错又不丢关键信息。机制详见 [[29.长对话裁剪无效时的处理方法及OpenClaw的Compaction策略]] 与 [[30.OpenClaw中Context管理抽象为可插拔Context Engine的原因及支持策略]]，记忆机制见 [[22.Agent系统中短期记忆与长期记忆的差异及存储检索方式]]。
