## Agent 系统幂等性的必要性及 OpenClaw 的 Gateway 幂等性处理方案

### 1. 什么是幂等性

幂等性（Idempotency）：**同一个请求执行一次和执行多次，产生的效果相同**。对 Agent 系统即——重复的请求/重试/消息重复投递，不会产生重复副作用（重复扣款、重复发邮件、重复写数据）。

### 2. 为什么 Agent 系统必须做幂等

Agent 会自主调用工具、多步执行、跨网络通信，重复几乎不可避免：

| 重复来源 | 场景 | 不幂等的后果 |
| --- | --- | --- |
| 网络重试 | 超时后重发请求 | 重复执行工具 |
| 用户重复点击 | 用户连点/刷新 | 重复提交任务 |
| 工具重复执行 | Agent 重试失败的工具 | 重复扣款/重复下单 |
| 消息重复投递 | 消息总线至少一次交付 | 同一任务跑多遍 |
| Gateway 转发重试 | 网关重试下游 Agent | 副作用翻倍 |
| 长任务中断恢复 | 恢复后重放 | 数据脏写 |

> Agent 调用的工具常有真实副作用（下单、付款、发消息、改库），不幂等会直接造成资损/数据错乱。

### 3. 通用幂等方案

| 方案 | 思路 |
| --- | --- |
| 请求 ID 去重 | 每个请求带唯一 ID，服务端记录已处理 ID，重复直接拒/回放 |
| 幂等键（Idempotency Key） | 业务侧用稳定的幂等键（如 `订单号+操作`），同键只执行一次 |
| 结果缓存回放 | 已处理请求缓存结果，重复请求直接返回缓存 |
| 状态机校验 | 执行前校验当前状态，已到目标态则跳过 |
| 数据库唯一约束 | 用唯一索引兜底防重复写 |
| 工具侧幂等 | 工具本身设计成幂等（如 upsert 代替 insert） |

### 4. OpenClaw 的 Gateway 幂等处理方案

OpenClaw 这类 Agent 框架的典型设计，把幂等收敛在 **Gateway** 层统一处理，下游 Agent/工具不必各自实现：

```
请求(带 request_id / idempotency_key)
        │
   ┌────▼─────┐
   │ Gateway  │
   │  幂等层  │ ──→ 命中缓存？─是─→ 直接回放历史结果（不重复执行）
   └────┬─────┘
        │ 否
   路由到 Agent → 执行 → 结果写幂等缓存 → 返回
```

| Gateway 幂等手段 | 说明 |
| --- | --- |
| 请求 ID 去重 | 请求带唯一 request_id，Gateway 记录已处理 ID，重复请求拦截 |
| 幂等键 | 业务幂等键（如 `task_id+step`）作为去重主键，同键只执行一次 |
| 结果缓存回放 | 已完成请求的结果缓存，重复请求直接返回缓存，不重跑 |
| 工具调用幂等控制 | Agent 重试工具时，带同一幂等键，工具侧据键去重 |
| 状态校验 | 执行前校验任务状态，已完成则跳过 |

### 5. 幂等键设计要点

| 要点 | 说明 |
| --- | --- |
| 稳定性 | 同一逻辑请求幂等键不变（不能用随机 UUID） |
| 唯一性 | 不同请求键不同 |
| 业务语义 | 优先用业务字段（订单号+操作类型）而非纯自增 |
| 缓存期限 | 结果缓存设合理 TTL，过期可重新执行 |
| 失败处理 | 处理失败不写成功缓存，允许重试；处理中加锁防并发重复 |

### 6. 幂等 vs 非幂等工具

| 工具类型 | 幂等性 | 处理 |
| --- | --- | --- |
| 查询类（读） | 天然幂等 | 无需特殊处理 |
| upsert/设值类 | 幂等 | 安全 |
| insert/扣款/发消息 | 非幂等 | 必须靠幂等键/去重保护 |

### 7. 一句话总结

Agent 系统因网络重试/重复点击/工具重试/消息重复投递而必须做幂等，否则重复副作用造成资损与脏数据；OpenClaw 这类框架在 **Gateway 层统一处理幂等**——请求 ID 去重、业务幂等键、结果缓存回放、工具调用幂等控制、状态校验，把幂等收敛在一处，下游不必各自实现。Gateway 角色见 [[42.多Agent间的通信协调方式及OpenClaw中Gateway的作用]]，工具结果处理见 [[28.Agent调用工具返回超大结果的问题及解决方案OpenClaw实操]]，工具权限见 [[37.Agent工具权限控制的设计及OpenClaw的工具策略管道分层]]。
