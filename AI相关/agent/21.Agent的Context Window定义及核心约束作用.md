## Agent 的 Context Window 定义及核心约束作用

### 1. Context Window 定义

Context Window（上下文窗口）= LLM **单次推理能处理的最大 token 数**，涵盖 System Prompt + 历史对话 + 工具结果 + 用户输入 + 模型输出。

| 模型量级 | 典型 Context Window |
| --- | --- |
| 早期 | 4K~8K |
| 主流 | 32K~128K |
| 长上下文 | 200K~1M+ |

> Context Window 是 Agent 的"工作台面积"——台子就那么大，东西多了就得往外搬或压缩。

### 2. 对 Agent 的核心约束

Agent 比单轮问答更吃上下文，因为它的上下文会**持续累积膨胀**：

| 膨胀来源 | 说明 |
| --- | --- |
| 多轮对话累积 | 每轮 Thought/Action/Observation 都追加，越聊越长 |
| 工具结果膨胀 | 一次搜索/代码执行可能返回数千 token |
| 记忆注入 | 长期记忆召回的内容要塞进上下文 |
| 工具 schema | 工具越多，定义越占空间 |

一旦总和超过 Context Window，就必须**截断**——而截断意味着信息丢失：

| 约束影响 | 后果 |
| --- | --- |
| 被迫截断早期内容 | 丢失任务目标/早期关键决策 |
| 工具结果被截 | 关键证据缺失，推理出错 |
| 记忆塞不进 | 长期记忆形同虚设 |
| token 成本 | 接近上限时每轮都贵 |

### 3. 应对策略

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| 压缩/摘要 | 把早期对话/工具结果摘要成精简版 | 历史轮次多时 |
| 外部长期记忆 | 把不常用的搬到外部存储，按需检索回来 | 跨会话/海量记忆 |
| 分块处理 | 大任务拆成子任务，每个子任务独立上下文 | 超长任务 |
| 工具结果裁剪 | 工具返回先过滤/截断再入上下文 | 工具结果大时 |
| 上下文管理 | 主动管理上下文生命周期（保留/摘要/丢弃） | 所有 Agent |

### 4. 上下文管理的基本思路

```
上下文总额 > Context Window?
  ├─ 否 → 直接用
  └─ 是 → 触发管理：
        ├─ 旧轮次 → 摘要压缩
        ├─ 大工具结果 → 裁剪/存外部
        ├─ 长期记忆 → 检索式按需召回
        └─ 仍超 → 分块/子任务隔离
```

### 5. 一句话总结

Context Window 是 LLM 单次处理的最大 token 数，对 Agent 而言是核心硬约束——多轮对话、工具结果、记忆注入会让上下文持续膨胀，超限截断则信息丢失；应对靠**压缩摘要 + 外部长期记忆 + 分块处理 + 工具结果裁剪 + 主动上下文管理**。记忆机制见 [[22.Agent系统中短期记忆与长期记忆的差异及存储检索方式]]，长期记忆实现见 [[12.LLM Agent长期记忆能力的实现方法]]，System Prompt 占用见 [[20.System Prompt在Agent系统中的职责及过长处理方法]]。
