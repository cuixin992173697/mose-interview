## 多渠道下 Agent 会话隔离粒度的设计及 OpenClaw 的实现

### 1. 会话隔离需求

多渠道接入后，必须保证不同用户、不同渠道、不同会话之间的**上下文与记忆不串、权限不越界**：

| 不隔离的后果 | 说明 |
| --- | --- |
| 上下文串 | A 用户的历史混进 B 用户的对话，泄露隐私 |
| 记忆串 | 长期记忆跨用户共享，A 看到 B 的偏好 |
| 权限越界 | 低权限用户用了高权限会话的工具/数据 |
| 状态错乱 | 同一用户多个会话互相干扰 |

### 2. 隔离粒度层级

OpenClaw 这类框架支持多级隔离粒度，从粗到细：

| 隔离粒度 | 隔离键 | 适用 | 风险 |
| --- | --- | --- | --- |
| 全局级 | 无 | 单租户 demo | 无隔离，严禁生产用 |
| 渠道级 | channel | 每渠道独立 Agent 实例 | 同渠道用户互相串 |
| 用户级 | (channel, user_id) | 每用户独立上下文/记忆 | 同用户多会话串 |
| 会话级 | (channel, session_id) | 每会话独立上下文（推荐默认） | 需处理跨会话记忆 |
| Agent 级 | (channel, session_id, agent_id) | 多 Agent 各自独立上下文 | 粒度最细，存储成本高 |

> 多租户系统还要在最外层加 `tenant_id`，形成 `(tenant_id, channel, ...)`。

### 3. OpenClaw 的实现

核心思路：**用隔离键对上下文、记忆、会话状态做分桶存储与检索**。

#### 隔离键设计

```
默认：     isolation_key = (channel, session_id)
带用户：   isolation_key = (channel, user_id, session_id)
多租户：   isolation_key = (tenant_id, channel, user_id, session_id)
```

| 隔离键组成 | 作用 |
| --- | --- |
| channel | 区分渠道（Web 消息不混入 IM） |
| user_id | 区分用户（同渠道不同用户不串） |
| session_id | 区分会话（同用户多会话不串） |
| tenant_id | 区分租户（多组织隔离） |

#### 分桶存储与检索

| 数据 | 存储方式 | 检索方式 |
| --- | --- | --- |
| 短期上下文（当前对话） | 按 isolation_key 分键存储 | 取该键的最近 N 轮 |
| 长期记忆 | 向量库按 isolation_key 打标签分区 | 该键范围内向量检索（见 [[12.LLM Agent长期记忆能力的实现方法]]） |
| 会话状态 | 按 isolation_key 存键值 | 按 key 读写 |

```
Agent 处理消息时：
  1. 从消息解析 isolation_key
  2. 用该 key 取上下文 + 检索记忆（只取该 key 范围内）
  3. 生成回复，新上下文/记忆写回该 key
  → 其他 key 的数据天然不可见，实现隔离
```

### 4. 隔离键设计要点

| 要点 | 说明 |
| --- | --- |
| 键的稳定性 | user_id / session_id 要跨消息稳定，否则隔离失效 |
| 跨会话记忆 | 会话级隔离下，长期记忆按 user_id 范围检索可跨会话复用（粒度可配） |
| 权限随隔离键 | 工具权限也按隔离键绑定，避免越权（见 [[37.Agent工具权限控制的设计及OpenClaw的工具策略管道分层]]） |
| 清理与保留 | 按 key 设置过期/容量上限，防存储膨胀 |

### 5. 一句话总结

多渠道会话隔离 = **按隔离键（默认 (channel, session_id)，可加 user_id / tenant_id）对上下文、记忆、会话状态分桶存储与检索**，粒度从全局到 Agent 级可选；OpenClaw 这类框架用隔离键保证不同用户/渠道/会话之间上下文与记忆不串、权限不越界。记忆机制见 [[22.Agent系统中短期记忆与长期记忆的差异及存储检索方式]]，多渠道接入见 [[31.Agent系统多渠道接入的抽象层设计及OpenClaw的Channel Plugin接口]]。
