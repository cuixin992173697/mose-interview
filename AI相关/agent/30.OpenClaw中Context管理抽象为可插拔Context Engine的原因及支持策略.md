## OpenClaw 中 Context 管理抽象为可插拔 Context Engine 的原因及支持策略

### 1. 什么是 Context Engine

Context Engine 是 OpenClaw 这类 Agent 框架中**专门负责上下文管理的抽象层**——把"如何组装/压缩/裁剪上下文"这一策略，从 Agent 的执行循环里剥离出来，独立成可替换的模块。

> 简单说：Agent 执行循环只管"推理→行动→观察"，**上下文怎么塞、塞多少、何时压缩**交给 Context Engine 决定。

### 2. 为什么抽象为可插拔

| 原因 | 说明 |
| --- | --- |
| 场景差异大 | 短对话/超长对话/多模态/多 Agent，各自最优上下文策略不同 |
| 便于替换 | 不同任务换不同策略，无需改执行循环 |
| 便于扩展 | 新增策略（如新的压缩算法）只需实现接口，不侵入主流程 |
| 便于测试 | 上下文策略可独立单测，与 Agent 解耦 |
| 便于调优 | 策略参数可独立调整，定位问题更快 |
| 解耦 | 上下文策略与执行循环解耦，各自演进 |

一句话：**把"上下文策略"当一等公民独立出来，才能按场景插拔、独立演进。**

### 3. Context Engine 的职责

| 职责 | 说明 |
| --- | --- |
| 上下文组装 | 决定 System Prompt / 历史 / 工具结果 / 记忆的拼接顺序与格式 |
| 压缩（Compaction） | 接近窗口阈值时对旧上下文结构化压缩，详见 [[29.长对话裁剪无效时的处理方法及OpenClaw的Compaction策略]] |
| 裁剪 | 必要时按策略丢弃低价值内容 |
| 记忆注入 | 从外置长期记忆检索相关内容并注入上下文 |
| Token 预算管理 | 监控当前 token 占用，决定何时触发压缩/裁剪 |

### 4. 支持的策略（可插拔切换）

| 策略 | 思路 | 适合场景 |
| --- | --- | --- |
| 滑动窗口 | 只保留最近 N 轮原文 | 短/中等对话 |
| 摘要压缩 | 旧对话摘要化 | 中长对话 |
| 重要性评分 | 按重要性打分，低分先丢 | 关键信息稀疏的长对话 |
| 分层记忆 | 近期原文+中期摘要+远期索引 | 超长对话 |
| 全量+检索混合 | 近期全量 + 远期外置检索注入 | 需回溯历史的长任务 |

不同策略可按场景插拔切换：短对话用滑动窗口省事，超长对话用分层记忆+外置检索。

### 5. 可插拔接口设计思路

Context Engine 作为抽象层，典型接口设计遵循"**输入当前上下文状态 → 输出处理后的上下文**"：

```
ContextEngine（接口）
├─ assemble(对话历史, 工具结果, 记忆) → 组装后的上下文
├─ check_budget(上下文) → 是否超阈值、需否压缩
├─ compact(上下文) → 压缩后的上下文 + 归档
└─ recall(query) → 从外置记忆检索相关内容

具体策略实现该接口：
├─ SlidingWindowEngine
├─ SummaryCompactionEngine
├─ LayeredMemoryEngine
└─ ... 按场景选用
```

| 设计要点 | 说明 |
| --- | --- |
| 统一接口 | 所有策略实现同一接口，执行循环无感知切换 |
| 策略可配置 | 通过配置选策略+调参数，不改代码 |
| 压缩可观测 | 压缩/裁剪动作可记录、可回溯，便于调试 |
| 记忆外置 | 长期记忆独立存储，Context Engine 只负责检索注入 |

### 6. 一句话总结

OpenClaw 把上下文管理抽象为可插拔的 Context Engine，是为了**按场景替换/扩展/调优上下文策略，且与执行循环解耦**；它负责组装、压缩、裁剪、记忆注入和 token 预算管理，支持滑动窗口/摘要压缩/重要性评分/分层记忆等策略插拔切换。压缩机制见 [[29.长对话裁剪无效时的处理方法及OpenClaw的Compaction策略]]，整体长对话方案见 [[27.LLM Context Window上下Agent长对话的实现及OpenClaw的解决方案]]，Context Window 约束见 [[21.Agent的Context Window定义及核心约束作用]]。
