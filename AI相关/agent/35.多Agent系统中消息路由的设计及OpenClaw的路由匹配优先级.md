## 多 Agent 系统中消息路由的设计及 OpenClaw 的路由匹配优先级

### 1. 多 Agent 路由需求

当一个系统里挂载多个 Agent（如客服 Agent、数据分析 Agent、代码 Agent、文档 Agent），每条用户消息进来后，必须先决定**交给哪个 Agent 处理**——这就是消息路由。

| 路由失败的后果 | 说明 |
| --- | --- |
| 路由错 | 消息给了不擅长该领域的 Agent，答非所问 |
| 不路由 | 所有 Agent 都抢着答，或没人答 |
| 路由慢 | 每条消息都走重型判断，延迟高、成本高 |

### 2. 路由设计方式

OpenClaw 这类 Agent 框架常见的四种路由方式：

| 路由方式 | 原理 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 规则路由 | 按显式规则（前缀/命令/正则/指定 Agent） | 快、确定、零成本 | 覆盖窄、写死 | 明确指令场景 |
| 关键词路由 | 命中关键词词典路由到对应 Agent | 简单、低成本 | 歧义词易误路由 | 术语清晰领域 |
| 语义向量路由 | query 与各 Agent 描述做向量相似度，取最高 | 泛化、抗表述差异 | 需 embedding、有误判 | 模糊语义场景 |
| LLM 意图路由 | 让 LLM 判断意图后选 Agent | 最灵活、能处理复杂意图 | 贵、慢 | 复杂多意图 |

### 3. OpenClaw 路由匹配优先级

单一方式都有短板，OpenClaw 采用**分层匹配**，从高到低依次尝试，命中即停：

```
入站消息
  │
  ▼
① 精确规则匹配（显式指定 @agent / 命令前缀 / 正则）——命中→路由
  │ 未命中
  ▼
② 关键词匹配（命中某 Agent 的关键词词典）——命中→路由
  │ 未命中
  ▼
③ 语义相似匹配（query 向量 vs 各 Agent 描述向量，取 Top1 且超阈值）——命中→路由
  │ 未命中/低于阈值
  ▼
④ LLM 意图兜底（让 LLM 在候选 Agent 中选一个）——必出结果
  │
  ▼
路由到目标 Agent
```

| 优先级 | 方式 | 成本 | 角色 |
| --- | --- | --- | --- |
| ① 最高 | 精确规则 | 极低 | 快速直送，省算力 |
| ② | 关键词 | 低 | 兜常见术语 |
| ③ | 语义向量 | 中 | 处理模糊语义 |
| ④ 最低 | LLM 意图 | 高 | 兜底保覆盖 |

### 4. 优先级设计理由

| 设计原则 | 体现 |
| --- | --- |
| 精确优先省成本 | 用户显式 `@code-agent` 这类指令，直接规则命中，不走任何模型，最快最省 |
| 由便宜到贵 | 规则→关键词→向量→LLM，成本递增，前面命中就不花后面的钱 |
| 兜底保覆盖 | LLM 意图兜底确保任何消息都有归属 Agent，不会"没人接" |
| 阈值防误路由 | 语义匹配需超相似度阈值，否则降级到 LLM 判断，避免低置信误路由 |

### 5. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 默认 Agent | 所有方式都未明确命中时，路由到一个默认通用 Agent |
| 路由可观测 | 记录每条消息命中的路由方式和目标，便于调优 |
| Agent 描述质量 | 语义/LLM 路由依赖各 Agent 的描述写得好坏，描述要清晰区分 |
| 动态增删 Agent | 路由表/向量索引要支持 Agent 热增删 |
| 多 Agent 协作 | 复杂任务可路由后由主 Agent 再分发子任务给其他 Agent（见 [[9.LLM Agent的基本架构组成]]） |

### 6. 一句话总结

多 Agent 路由 = **分层匹配优先级：精确规则 > 关键词 > 语义向量 > LLM 意图兜底**，从便宜到贵依次尝试、命中即停，精确优先省成本、LLM 兜底保覆盖；OpenClaw 这类框架用这套分层路由把消息准确交给目标 Agent。组件关系见 [[24.OpenClaw的核心组件及组件间关系]]。
