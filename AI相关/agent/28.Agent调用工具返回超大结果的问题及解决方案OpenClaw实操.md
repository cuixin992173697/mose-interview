## Agent 调用工具返回超大结果的问题及解决方案（OpenClaw 实操）

### 1. 问题：工具返回超大结果撑爆上下文

Agent 调用工具时，工具返回的结果会被追加进上下文。很多工具的返回体极大，远超预期：

| 场景 | 超大结果表现 |
| --- | --- |
| 搜索引擎 | 返回几十条结果，每条带长摘要，合计上万行 |
| 读大文件 | 读一个日志/CSV/源码文件，动辄几万行 |
| 数据库查询 | 全表查询返回海量行 |
| 网页抓取 | 抓一个页面，正文+导航+脚本混杂 |
| API 批量返回 | 一次拉取大量记录 |

后果：单次工具结果就可能**撑爆 Context Window**，导致后续推理报错或早期上下文被挤掉；即使没超限，大量低信噪比内容也会**稀释模型注意力**，降低回答质量。

### 2. 通用解决方案

| 方案 | 思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 结果截断 | 只取前 N 行/字符 | 简单 | 可能截掉关键部分 |
| LLM 摘要 | 让模型把结果压成摘要再入上下文 | 信噪比高 | 多一次 LLM 调用、有损 |
| 分页拉取 | 工具支持分页/limit，按需取下一页 | 精准控量 | 需多轮调用 |
| 流式处理 | 流式读取边处理边丢弃 | 省内存 | 实现复杂 |
| 落库后检索 | 结果落外部存储，只回填摘要+引用，按需二次检索原文 | 上下文极轻 | 依赖检索质量 |

### 3. OpenClaw 实操处理流程

OpenClaw 这类 Agent 框架的典型设计：工具结果**不直接全量塞进上下文**，而是先过 Context Engine 评估，按策略处理：

```
工具返回结果
   │
   ▼
Context Engine 评估结果大小与相关性
   │
   ├─ 小且高相关 → 直接回填上下文
   ├─ 大但有结构 → 压缩/摘要后回填
   ├─ 超大 → 落外部存储，只回填摘要+引用句柄
   └─ 需细查 → 分页/分块，按需二次检索原文
   │
   ▼
回填上下文（轻量化）→ 模型继续推理
   │
   └─ 模型若需原文细节 → 用句柄二次检索（按需召回）
```

| 处理分支 | 触发条件 | 回填内容 |
| --- | --- | --- |
| 直接回填 | 结果小且相关 | 完整结果 |
| 压缩回填 | 结果大但有结构 | 摘要/关键片段 |
| 落库+引用 | 结果超大 | 摘要 + 引用句柄（原文在外部存储） |
| 分页细查 | 需逐段查看 | 当前页 + 翻页能力 |

> 关键思想：**上下文里只放"模型现在需要的"，原文留在外部存储按需取**——这是控制上下文膨胀的通用工程原则（详见 [[30.OpenClaw中Context管理抽象为可插拔Context Engine的原因及支持策略]]）。

### 4. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 工具侧约束 | 工具实现就应支持 limit/分页/字段筛选，从源头控量 |
| 阈值策略 | 设结果 token 阈值，超阈值触发压缩/落库，阈值可配置 |
| 摘要保结构 | 表格/列表摘要时保留结构，别压成一坨 |
| 引用可溯源 | 落库后回填的引用句柄要能定位回原文，便于二次检索 |
| 避免无谓全量 | 能查列就别查全表，能读段就别读全文 |

### 5. 一句话总结

工具返回超大结果会撑爆上下文——OpenClaw 这类框架的实操是**让结果先过 Context Engine 评估，按大小/相关性选择直接回填、压缩摘要、落库+引用或分页细查**，上下文只保留模型当下所需，原文外置按需二次检索。Context Engine 机制见 [[30.OpenClaw中Context管理抽象为可插拔Context Engine的原因及支持策略]]，长对话整体方案见 [[27.LLM Context Window上下Agent长对话的实现及OpenClaw的解决方案]]，工具调用链路见 [[19.Tool Calling工具调用的完整链路解析]]。
