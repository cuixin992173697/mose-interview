## AI Agent 的 Skills 体系设计、管理及实际项目挑战

### 1. 体系设计

一个成规模的 Agent 系统会有几十上百个 Skill，需要体系化设计：

| 设计维度 | 说明 |
| --- | --- |
| 分类 | 按领域/职能分类（如"写作类""分析类""检索类"） |
| 层级 | 通用 Skill（基础能力）↔ 领域 Skill（业务能力）↔ 场景 Skill（具体任务） |
| 接口规范 | 统一的输入/输出/错误/元数据格式 |
| 元数据 | 名称、描述、版本、依赖、权限、输入输出 schema |
| 描述质量 | Skill 描述写得越清晰，Agent 选中率越高（类似工具描述） |

#### 接口规范示例

```yaml
skill:
  name: generate_weekly_report
  description: 根据本周数据生成技术周报
  inputs:
    - week_data: object (required)
  outputs:
    - report: markdown
  dependencies: [search, data_query]
  permission: report_write
  version: 1.2.0
```

### 2. 管理

| 管理环节 | 说明 |
| --- | --- |
| 注册 | 新 Skill 按规范注册到中心仓库 |
| 发现 | Agent 按任务检索/匹配可用 Skill（靠描述 + 元数据） |
| 版本 | 多版本共存、灰度、回滚 |
| 权限 | 哪些 Agent/用户可调用哪些 Skill |
| 依赖 | Skill 间依赖、Skill 依赖的工具/MCP 资源 |
| 监控 | 调用频次、成功率、耗时 |

### 3. 实际项目挑战与应对

| 挑战 | 表现 | 应对 |
| --- | --- | --- |
| 命名冲突 | 多团队 Skill 重名/语义重叠 | 统一命名规范 + 命名空间 + 中心注册 |
| 粒度权衡 | 太粗不灵活、太细等于没封装 | 按复用度/稳定度定粒度，高频稳定流程才封装 |
| 维护成本 | Skill 多了更新/测试负担大 | 版本管理 + 自动化测试 + 弃用淘汰机制 |
| 测试难 | Skill 含 LLM 调用，输出不确定 | 评测集 + 回归测试 + 关键路径断言 |
| 动态加载 | 运行时按需加载，避免全量加载撑爆上下文 | 按需注入描述 + 懒加载 |
| 权限安全 | Skill 可能含危险操作 | 权限分层 + 危险操作确认 + 审计日志 |
| 选中率 | Skill 多了 Agent 选错或选漏 | 描述优化 + 检索式匹配 + 评测命中率 |

### 4. 选型与演进建议

| 阶段 | 建议 |
| --- | --- |
| 起步 | 少量核心 Skill，先跑通 |
| 成长 | 按复用度逐步封装，建立规范 |
| 成熟 | 中心化仓库 + 版本/权限/监控 + 评测驱动淘汰 |

### 5. 一句话总结

Skills 体系要解决"多 Skill 怎么组织、管理、不出乱子"：设计上做**分类/层级/接口规范/元数据**，管理上做**注册/发现/版本/权限/依赖/监控**，项目里重点应对**命名冲突、粒度权衡、维护成本、测试、动态加载、权限安全、选中率**等挑战。基础概念见 [[32.AIAgent中Skills的定义及作用]]，与 MCP 的关系见 [[33.MCP与Skills的差异及适用场景]]。
