## LLM Agent 动态 API 调用的实现方式

### 1. 什么是动态 API 调用

动态 API 调用 = **Agent 在运行时根据当前任务，自主选择要调用的 API/工具，生成参数并执行**，而非代码里静态硬编码调用顺序。

| 维度 | 静态集成 | 动态调用（Agent） |
| --- | --- | --- |
| 调用决策 | 开发者写死 | LLM 运行时决定 |
| 参数 | 代码固定 | LLM 生成 |
| 顺序 | 固定流程 | 按需灵活 |
| 适配新任务 | 改代码 | 加工具描述即可 |

### 2. 实现链路

```
1. 工具描述注册      → 把可用 API 的名字/描述/参数 Schema 告诉 LLM
2. LLM 决策          → 根据任务推理要调哪个工具、传什么参数
3. 参数生成          → LLM 输出结构化调用（Function Calling）
4. 运行时执行        → 编排层真正调用 API，拿到结果
5. 结果回填          → 结果作为 Observation 注入上下文
6. LLM 继续推理      → 看结果决定下一步
```

### 3. 关键：工具描述 + Function Calling

#### 工具描述（让 LLM 知道有什么工具）

```json
{
  "name": "get_weather",
  "description": "查询指定城市的实时天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名"}
    },
    "required": ["city"]
  }
}
```

#### Function Calling（让 LLM 结构化输出调用）

模型收到工具描述后，输出结构化工具调用而非自然语言，编排层解析后执行：

```python
response = client.chat.completions.create(
    model="...",
    messages=[{"role": "user", "content": "北京今天下雨吗"}],
    tools=[weather_tool_spec],   # 注入工具描述
)
tool_call = response.choices[0].message.tool_calls[0]
# → {"name": "get_weather", "arguments": {"city": "北京"}}
result = execute(tool_call)       # 运行时真正执行
```

完整链路解析见 [[19.Tool Calling工具调用的完整链路解析]]。

### 4. 运行时执行与结果回填

- 编排层解析 tool_call → 校验（工具存在？参数对？权限？）→ 执行真实 API
- 结果格式化后作为 tool_result/Observation 回填上下文
- 失败也回填（错误信息），让 LLM 修正重试

### 5. 挑战与对策

| 挑战 | 对策 |
| --- | --- |
| 参数生成错误 | 参数 Schema 约束 + 校验 + 错误回填重试 |
| 工具选错 | 工具描述写清晰 + Rerank 候选工具 |
| 错误处理 | 错误作为 Observation，模型自主修正 |
| 权限控制 | 工具策略/白名单 + 危险操作人工确认 |
| 速率/成本 | 缓存、限流、分级路由 |
| 结果过大 | 截断/压缩/分页（见上下文管理相关篇） |

### 6. 一句话总结

动态 API 调用 = **工具描述注册 → LLM 运行时决策选工具 → Function Calling 生成结构化参数 → 编排层校验执行 → 结果回填上下文 → LLM 继续推理**；它让 Agent 灵活按需调用而非静态硬编码，关键靠工具描述质量和 Function Calling 机制，挑战在参数正确性、错误恢复与权限控制。
