## 超长模型上下文窗口限制的工程解决方案

### 1. 限制问题

LLM 的 Context Window（上下文窗口）有 token 上限，超了要么报错要么被截断丢信息。常见触发场景：

| 场景 | 表现 |
| --- | --- |
| 长文档问答 | 整篇塞不下，或塞下但语义被稀释 |
| 长对话 | 多轮累积超限，早期信息丢失 |
| Agent 工具结果累积 | 每轮工具返回叠加，迅速撑爆 |
| 多文档融合 | 多份资料拼一起超限 |
| 检索结果过多 | top-k 召回全塞进超限 |

### 2. 工程解决方案对比

| 方案 | 思路 | 适用 | 权衡 |
| --- | --- | --- | --- |
| RAG 外挂知识 | 不塞全量，按需检索相关片段进上下文 | 知识密集问答 | 依赖检索质量，见 rag 目录《04.详解RAG的完整工作流程》 |
| 摘要压缩 | 旧内容/长文档摘要化后再入上下文 | 长对话/长文档 | 摘要有损，关键细节可能丢 |
| 分层记忆 | 近期原文+中期摘要+远期外置索引 | 长对话 Agent | 实现复杂，见 agent 目录《22.短期记忆与长期记忆》 |
| 分块处理 | 大输入切成小块分批处理再合并 | 超长文档处理 | 合并逻辑要设计 |
| 上下文管理 Context Engine | 可插拔引擎动态管理预算/压缩/裁剪 | Agent 框架 | 见 agent 目录《27.LLM Context Window上下Agent长对话的实现及OpenClaw的解决方案》 |
| 滑动窗口 | 只留最近 N 轮/窗口 | 短期对话 | 早期信息全丢 |
| 长上下文模型 | 直接用百万 token 窗口模型 | 超长输入场景 | 成本高、延迟大、仍有上限，见 [[13.大模型上下文窗口扩展至100万token对现有业务场景的影响]] |

### 3. 各方案适用场景与权衡

| 关注点 | 偏好方案 |
| --- | --- |
| 要精确引用原文 | RAG（按需检索片段）+ 分块 |
| 要保留全程脉络 | 分层记忆 + 摘要压缩 |
| 要低成本 | 滑动窗口 + 摘要（少塞 token） |
| 要简单 | 滑动窗口 |
| 要极致覆盖 | 长上下文模型（贵） |

### 4. 组合策略（工业实践）

单一方案都不够，通常组合：

```
长输入 → 分块 → RAG 检索相关片段（精准） 
       → 旧部分摘要压缩（省 token）
       → 分层记忆外置（跨会话）
       → Context Engine 统一预算管理（动态裁剪）
       → 长上下文模型兜底（实在塞不下时）
```

| 组合 | 解决 |
| --- | --- |
| RAG + 分块 | 长文档精准问答 |
| 摘要 + 滑动窗口 | 长对话不超限 |
| 分层记忆 + 外置检索 | Agent 长任务记忆 |
| Context Engine + Compaction | Agent 上下文动态压缩 |

### 5. 一句话总结

上下文窗口限制的工程解法 = **RAG 按需检索 + 摘要压缩 + 分层记忆外置 + 分块处理 + Context Engine 动态管理 + 长上下文模型兜底**，工业上多组合使用而非单押；Agent 长对话的上下文管理见 agent 目录《21.Agent的Context Window定义及核心约束作用》《27.LLM Context Window上下Agent长对话的实现及OpenClaw的解决方案》，百万 token 窗口的影响见 [[13.大模型上下文窗口扩展至100万token对现有业务场景的影响]]。
