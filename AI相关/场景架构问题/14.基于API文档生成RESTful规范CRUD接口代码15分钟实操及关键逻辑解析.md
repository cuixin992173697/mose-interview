## 基于 API 文档生成 RESTful 规范 CRUD 接口代码 15 分钟实操及关键逻辑解析

场景：给 LLM 一份数据模型 + API 文档，让它按 RESTful 规范、指定技术栈，15 分钟生成可用的 CRUD 接口代码（Controller/Service/Model + 校验 + 错误处理）。关键不在"能生成"，而在 Prompt 约束得够规范、生成后能直接跑。

### 1. 15 分钟实操步骤

| 步骤 | 用时 | 动作 |
| --- | --- | --- |
| ① 输入数据模型 + API 文档 | 2 min | 给 LLM 数据模型（字段/类型/约束）+ 接口需求 |
| ② Prompt 约束 RESTful 规范 + 技术栈 | 3 min | 明确 RESTful 规范、框架（如 Spring Boot/NestJS/Express）、校验库、错误结构 |
| ③ 生成 Controller/Service/Model + 校验 + 错误处理 | 6 min | LLM 一次性生成分层代码 |
| ④ 测试与微调 | 4 min | 跑通 + 修边界（校验/状态码/分页） |

### 2. 关键逻辑解析

| 要点 | 规范 |
| --- | --- |
| 资源命名 | 复数名词：`/users`、`/orders`，非动词 |
| HTTP 方法语义 | GET 查询 / POST 新增 / PUT 全量更新 / PATCH 部分更新 / DELETE 删除 |
| 路径参数 vs 查询参数 | `/users/{id}` 定位资源；`?page=&size=&sort=` 过滤分页 |
| 状态码 | 200/201 创建/204 无内容/400 参数错/404 不存在/409 冲突/500 服务错 |
| 分页排序过滤 | `?page=1&size=20&sort=-createdAt&status=active` |
| 参数校验 | 字段非空/长度/格式/范围，校验失败返 400 + 字段级错误 |
| 统一错误结构 | `{code, message, details}` 全局异常处理统一封装 |
| 版本控制 | URL 版本 `/api/v1/users` 或 Header 版本 |
| 幂等性 | GET/PUT/DELETE 幂等；POST 不幂等 |

### 3. 完整 Prompt 模板

```text
你是一名资深后端工程师。请根据下方数据模型与 API 文档，生成符合 RESTful 规范的 CRUD 接口代码。

技术栈：Node.js + Express + TypeScript + Zod 校验
分层：Controller（路由+参数校验）→ Service（业务）→ Model（数据访问）
要求：
1. 资源路径用复数名词，HTTP 方法符合语义（GET/POST/PUT/DELETE）。
2. 正确状态码：创建 201、删除 204、参数错 400、不存在 404、冲突 409。
3. 用 Zod 做请求体/参数校验，失败返 400 + 字段级错误。
4. 全局错误处理中间件，统一返回 {code, message, details}。
5. 列表接口支持分页 ?page=&size=、排序 ?sort=、过滤 ?status=。
6. 路径前缀 /api/v1。

【数据模型】
User: { id: number; name: string(2-20); email: string(email格式); age: number(0-150); status: "active"|"inactive" }

【API 文档】
- GET    /api/v1/users        列表（分页/排序/过滤）
- GET    /api/v1/users/:id    详情
- POST   /api/v1/users        创建
- PUT    /api/v1/users/:id    全量更新
- DELETE /api/v1/users/:id    删除

请输出：Controller、Service、Model、错误处理中间件、Zod schema 的完整代码。
```

### 4. 生成代码示例（关键部分）

```typescript
// ---- Zod 校验 schema ----
import { z } from "zod";

export const createUserSchema = z.object({
  name: z.string().min(2).max(20),
  email: z.string().email(),
  age: z.number().int().min(0).max(150),
  status: z.enum(["active", "inactive"]).default("active"),
});

// ---- Controller ----
import { Router, Request, Response, NextFunction } from "express";

export const userRouter = Router();

// 列表：分页/排序/过滤
userRouter.get('/', (req, res) => {
  const { page = 1, size = 20, sort, status } = req.query;
  const result = userService.list({
    page: +page, size: +size, sort: sort as string, status: status as string,
  });
  res.json(result);  // { data, total, page, size }
});

// 详情
userRouter.get('/:id', (req, res, next) => {
  const user = userService.getById(+req.params.id);
  if (!user) return res.status(404).json({ code: 404, message: 'User not found' });
  res.json(user);
});

// 创建
userRouter.post('/', (req, res, next) => {
  const parsed = createUserSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({
      code: 400, message: 'Validation failed',
      details: parsed.error.flatten().fieldErrors,
    });
  }
  try {
    const user = userService.create(parsed.data);
    res.status(201).json(user);
  } catch (e) { next(e); }
});

// 更新
userRouter.put('/:id', (req, res) => {
  const parsed = createUserSchema.safeParse(req.body);
  if (!parsed.success) return res.status(400).json({ code: 400, message: 'Validation failed', details: parsed.error.flatten().fieldErrors });
  const user = userService.update(+req.params.id, parsed.data);
  if (!user) return res.status(404).json({ code: 404, message: 'User not found' });
  res.json(user);
});

// 删除
userRouter.delete('/:id', (req, res) => {
  const ok = userService.delete(+req.params.id);
  if (!ok) return res.status(404).json({ code: 404, message: 'User not found' });
  res.status(204).send();
});

// ---- 全局错误处理中间件 ----
export function errorHandler(err: any, _req: Request, res: Response, _next: NextFunction) {
  res.status(err.status || 500).json({
    code: err.status || 500,
    message: err.message || 'Internal Server Error',
    details: err.details,
  });
}
```

### 5. 实操要点与坑

| 要点 | 说明 |
| --- | --- |
| Prompt 要明确技术栈 | 不指定框架/校验库，生成代码风格混乱难复用 |
| 约束分层 | 要求 Controller/Service/Model 分层，生成代码才清晰可维护 |
| 校验与错误结构必须约束 | 否则生成的代码常缺校验或错误格式不统一 |
| 生成后必测 | LLM 常在状态码、分页边界、幂等上出错，需人工校验微调 |
| 复用 Prompt 模板 | 模板固化后，换数据模型即可批量生成，效率稳定 |

### 6. 一句话总结

基于 API 文档生成 RESTful CRUD = **用结构化 Prompt 约束技术栈+分层+RESTful 规范（资源复数/HTTP 语义/状态码/校验/统一错误/分页）→ LLM 一次性生成 Controller/Service/Model+校验+错误处理 → 人工测边界微调**，关键是 Prompt 约束得够规范，生成代码才能直接跑、好维护。
