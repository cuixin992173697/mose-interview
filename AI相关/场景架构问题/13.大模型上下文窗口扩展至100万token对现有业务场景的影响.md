## 大模型上下文窗口扩展至 100 万 token 对现有业务场景的影响

Gemini、Claude 等模型上下文窗口已可达 100 万~200 万 token。窗口暴涨不是单纯"能塞更多"——它重塑了 RAG、Agent、成本、延迟、精度等多个业务决策。结论先说：**长上下文与 RAG 互补而非替代**。上下文窗口的基础约束见 agent 目录的《21.Agent的Context Window定义及核心约束作用》，工程解决方案见 [[7.超长模型上下文窗口限制的工程解决方案]]。

### 1. 长上下文模型现状

| 模型 | 上下文窗口 |
| --- | --- |
| Gemini 1.5/2.0 Pro | 100 万~200 万 token |
| Claude（部分版本） | 20 万~100 万 token |
| GPT-4o | 12.8 万 token |
| 趋势 | 窗口持续扩张，向"整本书/整库"迈进 |

### 2. 对业务的影响

| 维度 | 影响 | 说明 |
| --- | --- | --- |
| ① RAG 是否还需要 | **仍需要，但角色变** | 单份长文档可直塞无需切片检索；但海量知识库（百万文档）仍超窗口，必须 RAG |
| ② 成本 | token 费用激增 | 长上下文按 token 计费，塞 100 万 token 单次成本很高 |
| ③ 延迟 | 推理变慢 | prefill 长 prompt 慢，首 token 延迟显著上升 |
| ④ 精度 | lost-in-the-middle | 长上下文中段信息召回率下降，并非"塞了就记得" |
| ⑤ 新增场景 | 解锁超长输入 | 全库分析/超长代码库/长视频/长对话不截断 |

### 3. 哪些场景变 / 不变 / 新增

| 类别 | 场景 | 说明 |
| --- | --- | --- |
| 变（弱化 RAG） | 单份长文档问答（百页 PDF/合同/手册） | 可整篇直塞，不必切片检索，省去 RAG 建库 |
| 变（简化） | 长对话 | 不必频繁摘要压缩，长历史可直接带 |
| 不变（仍需 RAG） | 海量知识库问答（万级以上文档） | 知识总量远超窗口，仍需检索缩小范围 |
| 不变（仍需 RAG） | 实时更新知识 | 长上下文不解决"知识时效"，仍要外挂库 |
| 新增 | 全库一次性分析 | 跨文档比对/全局统计/全书总结 |
| 新增 | 超长代码库理解 | 整个仓库塞入做跨文件理解/重构 |
| 新增 | 长视频/长音频理解 | 多模态长输入一次性处理 |
| 新增 | Agent 长程任务 | 长任务轨迹不截断，减少记忆丢失 |

### 4. 为什么长上下文不能取代 RAG

| 理由 | 说明 |
| --- | --- |
| 知识量级 | 企业知识库动辄百万文档，100 万 token 装不下 |
| 成本 | 每次请求塞百万 token 成本高，RAG 只塞相关片段便宜得多 |
| 延迟 | 长上下文推理慢，RAG 短上下文快 |
| 精度 | lost-in-the-middle 使长上下文中段召回差，RAG 精选片段反而更准 |
| 时效 | 长上下文是训练时知识，RAG 接实时库才能答最新 |
| 更新 | 知识更新只需改库，不用换模型/重塞 |

### 5. 结论：长上下文与 RAG 互补

| 场景 | 最优选择 |
| --- | --- |
| 单份长文档、小知识集 | 长上下文直塞，免 RAG |
| 海量知识库 | RAG 检索缩小范围，长上下文容纳召回片段 |
| 实时/频繁更新知识 | RAG 外挂库 |
| 超长单输入（代码库/视频） | 长上下文 |
| 高精度问答 | RAG 精选 + Rerank，比长上下文中段更可靠 |

> 趋势：长上下文让 RAG 的"切片粒度"可以更粗（不必切太碎）、召回片段可以更多（窗口装得下），但"检索缩小范围 + 精排"的核心价值依旧在。

### 6. 一句话总结

100 万 token 窗口让**单份长文档可直塞、长对话可不截断、解锁全库/长代码/长视频新场景**，但面对海量知识库、成本、延迟、lost-in-the-middle 与时效问题，RAG 仍不可替代——长上下文与 RAG 是互补关系：长上下文容纳，RAG 检索缩小范围并控成本。
