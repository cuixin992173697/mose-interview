## RAG 调优后效果评估的方法及实际应用中的评估标准

### 1. 为什么需要评估

RAG 是一条多环节管道（切片→检索→Rerank→生成），**任何一环调参都会影响最终效果**。没有评测就只能凭感觉调参（盲调），有了评测才能定位瓶颈、量化收益、做 A/B。

评估的核心原则：**分层评估**——检索层、生成层、端到端各算各的，才能定位"是检索没召回，还是生成没答好"。

### 2. 检索层评估

评估"召回的准不准、全不全"，需人工标注的"标准答案片段（golden context）"。

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| Recall@k | top-k 里命中标准答案片段的比例 | 召全了没（最关键） |
| Precision@k | top-k 里相关片段的占比 | 召准了没 |
| MRR（Mean Reciprocal Rank） | 第一个相关片段排名倒数的均值 | 相关的排得靠不靠前 |
| NDCG@k | 考虑排名位置的相关性加权得分 | 排序质量（带相关性分级） |
| Hit Rate@k | top-k 里至少命中一个相关的 query 占比 | 有没有命中 |

> 调切片/embedding/混合检索权重/Rerank 时，主要看检索指标（尤其 Recall@k）。

### 3. 生成层评估

评估"生成的答案好不好"，需"标准答案（golden answer）"或借助 LLM 评判。

| 指标 | 含义 |
| --- | --- |
| Faithfulness（忠实度） | 答案是否**仅基于**召回上下文，有无捏造（反幻觉核心指标） |
| Answer Relevancy（答案相关性） | 答案是否切题、是否回答了问题 |
| Answer Correctness（准确性） | 答案与标准答案的一致程度 |
| Hallucination Rate（幻觉率） | 无依据断言占比 |
| Context Precision/Recall | 召回上下文对生成是否有用（衔接检索与生成） |

### 4. RAGAS 框架（主流自动化评估）

RAGAS 是 RAG 评测的事实标准，四大核心指标：

| 指标 | 评估什么 | 依赖 |
| --- | --- | --- |
| Faithfulness | 答案是否忠于上下文 | query + context + answer |
| Answer Relevancy | 答案是否切题 | query + answer |
| Context Precision | 召回上下文是否相关、排序是否合理 | query + context |
| Context Recall | 召回上下文是否覆盖标准答案 | query + context + golden answer |

- 优点：无需大量人工，用 LLM-as-judge 自动打分，可集成进 CI 持续评测。
- 局限：LLM 评判有偏差，关键场景仍需人工复核。

### 5. 端到端评估

| 方法 | 说明 |
| --- | --- |
| 人工评测 | 业务专家按 rubric 打分，金标准但贵、慢 |
| LLM-as-judge | 用更强模型评判答案质量，规模化但需校准偏差 |
| 用户反馈 | 点赞/点踩/修正，真实但稀疏、有偏 |
| 在线 A/B | 不同配置分流对比业务指标 |

### 6. 实际应用中的评估标准（业务指标）

工业落地最终看业务指标，技术指标只是手段：

| 业务指标 | 含义 | 说明 |
| --- | --- | --- |
| 准确率 | 答案正确的比例 | 核心红线 |
| 引用命中率 | 答案引用的出处真实存在且支持该结论的比例 | 可信度核心 |
| 拒答率 | 知识库无依据时正确拒答的比例 | 比乱答更重要 |
| 幻觉率 | 无依据断言占比 | 越低越好 |
| 首字延迟 / 端到端延迟 | 用户等待时间 | 体验底线 |
| 单 query 成本 | token + 检索 + 模型费用 | 商业可行性 |
| 召回率 / 覆盖率 | 能答的问题占比 | 知识库完备性 |

> 实践中常定阈值卡线：如"准确率≥90%、拒答率合理、p95 延迟≤3s、单 query 成本≤X"。

### 7. 评测集构建

| 要点 | 说明 |
| --- | --- |
| 覆盖典型 query 类型 | 事实型/对比型/多跳型/列表型/拒答型都要有 |
| 含"无答案"负样本 | 测拒答能力，防止硬编 |
| 标注 golden context + golden answer | 检索与生成都要能评 |
| 规模 | 起步几十到几百条，关键场景上千 |
| 持续扩充 | 线上 badcase 回流进评测集，迭代闭环 |
| 防数据泄露 | 评测集别混进训练/调参依据 |

### 8. 评估流程闭环

```
评测集（含 golden）→ 跑 RAG → 检索指标 + 生成指标(RAGAS) + 业务指标
   → 定位瓶颈（检索差？生成差？）→ 调参 → 再评测 → 对比迭代
```

| 症状 | 可能瓶颈 | 调优方向 |
| --- | --- | --- |
| Recall 低 | 检索召回不足 | 切片/混合检索/查询扩展 |
| Recall 高但 NDCG 低 | 排序差 | Rerank |
| 上下文相关但答案错 | 生成问题 | Prompt/换模型 |
| 答案脱离上下文 | 幻觉 | 强化 faithfulness、溯源约束 |

> 评估贯穿 [[04.详解RAG的完整工作流程]] 的"后处理与评测闭环"环节。

### 9. 一句话总结

RAG 评估 = **分层（检索 recall/MRR/NDCG + 生成 faithfulness/relevancy via RAGAS + 端到端业务指标）+ 评测集驱动迭代**，技术指标定位瓶颈、业务指标卡上线标准，没有评测集的 RAG 调参都是盲调。
