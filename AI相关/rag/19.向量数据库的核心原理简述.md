## 向量数据库的核心原理简述

### 1. 本质：为高维向量而生的专用数据库

向量数据库（Vector Database）是专门用于**存储、索引、检索高维向量**的数据库。它把文本/图像/音频经 Embedding 模型转换成的高维稠密向量（如 768/1536 维）作为一等公民来管理，并围绕"向量相似度检索"做深度优化。

```
文本/图片 → Embedding → 高维向量 → 存入向量库（建 ANN 索引）→ 相似度检索
```

### 2. 核心能力

| 能力 | 说明 |
| --- | --- |
| 向量存储 | 高效存储海量高维向量，通常配合原始文本/元数据一起存 |
| ANN 近似最近邻检索 | 在百万~亿级向量中毫秒级找到与查询向量最相似的 top-k（见 [[21.向量数据库中ANN的定义及应用价值]]） |
| 相似度度量 | 支持余弦/欧氏/内积等多种度量（见 [[22.向量数据库中余弦相似度、欧几里得距离、曼哈顿距离的定义及差异]]） |
| 元数据过滤 | 检索时按来源/时间/权限等元数据先过滤再相似度排序，兼顾精度与安全 |
| 增删改 | 支持向量与元数据的实时增删改，维护索引一致性 |
| 持久化与分布式 | 分片（sharding）、副本（replication）、持久化存储，支撑水平扩展与高可用 |

### 3. 工作原理（四步）

| 步骤 | 动作 | 产出 |
| --- | --- | --- |
| ① 向量化 | 文本经 Embedding 模型编码成稠密向量 | 文本-向量对 |
| ② 入库建索引 | 向量存入库，构建 ANN 索引（HNSW/IVF 等），元数据一并写入 | 可检索的向量库 |
| ③ 查询检索 | query 向量化后，做 ANN 检索 + 可选元数据过滤 | top-k 相似向量 |
| ④ 返回结果 | 返回相似向量对应的原始文本 + 元数据 + 相似度分数 | 候选片段列表 |

### 4. 为什么不用传统数据库

传统数据库（MySQL/PostgreSQL）的 B+ 树索引是为**精确匹配与范围查询**设计的，对"向量相似度"这种高维空间检索无能为力：

| 维度 | 传统数据库 | 向量数据库 |
| --- | --- | --- |
| 检索方式 | 精确匹配 / 范围扫描 | 相似度近似检索（ANN） |
| 索引结构 | B+ 树 / 哈希 | HNSW / IVF / LSH / PQ（见 [[20.向量数据库中HNSW、LSH、PQ的含义]]） |
| 高维 kNN | 暴力计算 O(N·D)，亿级数据不可行 | ANN 索引，毫秒级返回 |
| 语义检索 | 不支持 | 原生支持 |
| 代价 | 精确但无法扩展到大规模向量 | 牺牲少量精度换大幅提速 |

> 核心矛盾：高维向量的**精确最近邻（kNN）**需要和库里每个向量算距离，数据量一大就崩。向量数据库靠 ANN 索引把这一步从 O(N) 降到近似 O(logN)，这是它存在的根本理由。pgvector 这类插件是给传统库加 ANN 能力，本质还是同一思路。

### 5. 常见向量数据库

| 向量库 | 特点 |
| --- | --- |
| Milvus | 开源、分布式、生态全，企业级首选 |
| Pinecone | 全托管 SaaS，开箱即用 |
| Chroma | 轻量、本地开发友好，LangChain 常用 |
| Qdrant | Rust 实现、高性能、过滤强 |
| Weaviate | 内置混合检索与模块化 vectorizer |
| pgvector | PostgreSQL 扩展，复用现有 PG 运维 |

选型思路见 [[35.RAG项目中Milvus、Pinecone、Chroma向量数据库的选型思路]]，与必要性/差异见 [[33.RAG中向量数据库的必要性及与传统数据库的差异]]，完整工作流程见 [[23.向量数据库的核心工作流程]]。

### 6. 一句话总结

向量数据库 = **专门存高维向量 + 靠 ANN 索引做毫秒级相似度检索 + 支持元数据过滤**的专用数据库；它之所以必要，是因为传统数据库的精确匹配范式无法应对高维向量的海量相似度检索，必须靠 ANN 索引把复杂度降下来。
