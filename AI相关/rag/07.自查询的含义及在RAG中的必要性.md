## 自查询的含义及在 RAG 中的必要性

### 1. 什么是自查询（Self-Querying）

自查询 = 让 LLM 把用户的自然语言 query **拆成两部分**：

- **语义检索词（semantic_query）**：用于向量相似度检索的文本部分；
- **结构化过滤条件（metadata filter）**：用于元数据精确过滤的条件。

```
"2023年关于RAG的论文"
   ↓ 自查询拆解
semantic_query = "RAG"
filter = { year: == 2023 }
   ↓ 先过滤再检索
向量库中 year=2023 的文档里，按 "RAG" 做相似度检索
```

也叫 Query Construction（查询构造），本质是 **"自然语言 → 结构化检索表达式"** 的转换。

### 2. 为什么需要自查询

纯语义/向量检索有个硬伤：**它只能算"语义像不像"，算不了"等于不等于、在不在范围内"**。

| 用户真实意图 | 纯向量检索的问题 | 自查询如何解决 |
| --- | --- | --- |
| "2023 年的" | 把"2023"语义化，可能召回 2022/2024 的相关文档 | filter: year==2023 精确过滤 |
| "张三写的" | 召回一堆"张三"相关但非其撰写的文档 | filter: author=="张三" |
| "合同类" | 召回内容像合同但类别不是的文档 | filter: category=="合同" |
| "评分>4 的" | 向量无法表达数值大小比较 | filter: rating>4 |
| "销售部的" | 召回提到销售部但不属于该部门的文档 | filter: department=="销售" |

一句话：**向量检索擅长"模糊语义匹配"，不擅长"精确条件筛选"——自查询把后者补上。**

### 3. 实现方式

#### 标准流程

```
用户 query
   ↓ LLM（带元数据 schema 提示）
{ semantic_query, filter }
   ↓
向量库：filter 预过滤 → semantic_query 向量检索 top-k
```

#### 关键：给 LLM 喂元数据 schema

要让 LLM 正确拆出 filter，必须在 Prompt 里告诉它**有哪些字段、什么类型、可选值**：

```python
# LangChain SelfQueryRetriever 思路
metadata_field_info = [
    {"name": "year", "description": "发表年份", "type": "integer"},
    {"name": "author", "description": "作者", "type": "string"},
    {"name": "category", "description": "文档类别", "type": "string",
     "enum": ["论文", "合同", "报告"]},
]
retriever = SelfQueryRetriever.from_llm(
    llm, vectorstore, document_contents="论文摘要", 
    metadata_field_info=metadata_field_info
)
docs = retriever.invoke("2023年张三关于RAG的论文")
# LLM 拆出: semantic="RAG", filter= year==2023 AND author=="张三"
```

#### Filter 的常见操作

| 操作 | 示例 | 说明 |
| --- | --- | --- |
| 等于 | year==2023 | 精确匹配 |
| 范围 | rating>4, price<100 | 数值比较 |
| 属于 | category in [论文, 报告] | 多值枚举 |
| 组合 | year>=2023 AND author=="张三" | AND/OR 嵌套 |

### 4. 必要性论证

| 维度 | 不用自查询 | 用自查询 |
| --- | --- | --- |
| 精确条件 | 向量"算不出"等于/范围，召回噪声多 | 结构化过滤，精确无误 |
| 检索精度 | 语义相似的噪声混入 top-k | 先过滤再检索，precision↑ |
| 安全/权限 | 无法按权限/部门隔离 | filter 限定可见范围 |
| 性能 | 全库检索再人工筛 | 先过滤缩小候选集，更快更省 |
| 可解释 | 用户不知道为何召回这些 | filter 可回显，可解释 |

> 自查询是"元数据过滤"的自动化入口，元数据过滤的更多细节见 [[34.RAG系统利用元数据过滤提升检索精度的方法]]。

### 5. 与相关概念的区别

| 概念 | 做什么 |
| --- | --- |
| 自查询 | 拆出 semantic + 结构化 filter |
| 查询扩展 | 补词扩大召回（见 [[06.查询扩展的定义及在RAG中的应用价值]]） |
| 查询改写 | 换表述修正 query（见 [[43.RAG中Query Rewriting查询重写的定义及检索效果优化方法]]） |
| 意图路由 | 判断走哪个知识库/是否检索 |

### 6. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 元数据 schema 要全 | 字段名、类型、枚举值、描述都要喂给 LLM，否则拆不准 |
| filter 容错 | LLM 可能拆错/拆空，需校验字段合法性，解析失败则退化为纯语义检索 |
| 元数据质量 | 入库时元数据必须准确标注，否则 filter 形同虚设（见 [[04.详解RAG的完整工作流程]]） |
| 与 Rerank 配合 | 自查询保 precision，Rerank 进一步精排 |
| 性能 | 先 filter 缩小集再做 ANN，比全库检索更快 |

### 7. 一句话总结

自查询 = **用 LLM 把自然语言 query 拆成"语义检索词 + 结构化元数据 filter"**，让向量检索在"模糊语义匹配"之外获得"精确条件筛选"能力，是 RAG 提升检索精度、支持权限与范围过滤的必要手段。
