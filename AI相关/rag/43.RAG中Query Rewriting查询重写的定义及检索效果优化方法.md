## RAG 中 Query Rewriting 查询重写的定义及检索效果优化方法

### 1. 什么是 Query Rewriting（查询重写）

Query Rewriting = **在检索前，把用户的原始 query 改写成一个（或多个）更利于检索的表述**，再拿改写后的 query 去向量库/BM25 检索。

```
原始 query → [重写模块] → 改写 query → 检索 → 召回
```

它属于 RAG 在线流程中"查询理解"环节的核心技术（见 [[04.详解RAG的完整工作流程]]），目标是用一个"更匹配知识库文档表述"的问题去检索。

### 2. 为什么需要查询重写

用户原始问题往往"又短又糙又带指代"，直接检索效果差：

| 原始问题的问题 | 直接检索的后果 | 重写如何补救 |
| --- | --- | --- |
| 口语化/简略 | 与文档书面表述不匹配，召回不到 | 改写成书面完整表述 |
| 多轮指代（"它/那个"） | 指代词无实义，检索拿不到实体 | 把指代还原成实体 |
| 信息不足/模糊 | 检索方向偏，召回噪声 | 补全为明确问题 |
| 与文档表述不一致 | 词面/角度对不上 | 改成贴近文档的表述 |
| 复合问题 | 一次检索难覆盖 | 拆成子问题分别检索 |

### 3. 常见重写方法

#### 方法一：LLM 单次改写

让 LLM 把原始 query 改写成一个更利于检索的标准问法。

```python
rewrite_prompt = "请把以下用户问题改写成一个更清晰、更适合检索文档的表述，保留原意：\n问题：{question}\n改写："
```

简单直接，适合口语化/简略问题的规范化。

#### 方法二：Multi-Query（多查询生成）

让 LLM 针对同一意图生成**多个等价问法**，各路并行检索后融合结果。

| 维度 | 说明 |
| --- | --- |
| 做法 | LLM 生成 3~5 个不同角度/措辞的 query |
| 检索 | 每个 query 各召回 top-K，合并去重 |
| 优势 | 多角度覆盖，召回率显著↑，缓解单一表述漏召回 |
| 代价 | 多次检索 + 一次 LLM 调用，延迟与成本↑ |
| 融合 | 常用 RRF 融合多路结果（见 [[03.混合检索的定义及在大模型应用中的核心作用]]） |

#### 方法三：Step-back Prompting（后退提问）

当问题太具体、文档表述偏宏观时，让 LLM 先抽象出一个**更宽泛的"后退"问题**，先检索背景知识再答具体问题。

- 例：问"2024 年 Q3 某公司净利润"，先退一步问"该公司财务报告结构"，检索到报表结构背景后更易定位数字。

#### 方法四：HyDE（Hypothetical Document Embeddings）

让 LLM 先针对 query **假设一个答案（伪文档）**，再用这个伪答案去向量库检索。

| 维度 | 说明 |
| --- | --- |
| 直觉 | 答案比问题更接近文档的表述风格，检索更准 |
| 流程 | query → LLM 生成假设答案 → 假设答案向量化 → 检索文档 |
| 适用 | query 与文档表述差异大、但答案方向明确的场景 |
| 风险 | 假设答案跑偏会带偏检索，对 LLM 质量敏感 |

#### 方法五：历史改写（多轮指代消解）

多轮对话中把"它/那个/上面提到的"还原成具体实体，生成一个无指代的独立 query 再检索。

```
历史：用户问过"Transformer 的自注意力是什么"
当前："它的计算复杂度呢？"
重写 → "Transformer 自注意力的计算复杂度是多少？"
```

这是多轮 RAG 的必备环节（LangChain 的 `create_history_aware_retriever` 即做此事，见 [[41.RAG的定义及基于LangChain的RAG应用实现]]）。

### 4. 对检索效果的优化

| 效果 | 说明 |
| --- | --- |
| 召回率↑ | 改写后更贴近文档表述，原本召回不到的能召回了 |
| 相关性↑ | 去除指代/噪声词后，检索方向更准 |
| 抗表述差异 | 用户口语 ↔ 文档书面、同义改写都能兜住 |
| 多角度覆盖 | Multi-Query 多路并行，缓解单一表述漏召回 |

> 改写是把"用户语言"翻译成"文档语言"，是从根上提升召回质量的一步，常与混合检索、Rerank 叠加使用。

### 5. 与查询扩展（Query Expansion）的区别

二者常被混淆，但侧重不同：

| 维度 | Query Rewriting（重写） | Query Expansion（扩展） |
| --- | --- | --- |
| 本质 | **换表述**，生成新的等价 query | **加词**，在原 query 上补同义词/相关词 |
| 输出 | 一个/多个新 query | 原 query + 扩展词 |
| 目的 | 让问题更清晰、更贴近文档 | 扩大召回面，覆盖更多表述 |
| 关联 | 详见 [[06.查询扩展的定义及在RAG中的应用价值]] | — |

二者可组合：先重写再扩展，或 Multi-Query 时对每个子 query 做扩展。

### 6. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 何时启用 | query 简略/带指代/与文档表述差异大时收益高；简单明确 query 可跳过省成本 |
| 改写质量 | 改写跑偏会带偏整条链路，需评测改写后召回率是否提升 |
| 成本权衡 | Multi-Query/HyDE 多一次 LLM 调用 + 多次检索，对延迟敏感场景慎用或加缓存 |
| 与 Rerank 配合 | 重写扩大召回面，Rerank 保证精度，组合拳效果最佳 |
| 失败兜底 | 改写后仍召回不到时，走未命中处理方案（见 [[44.RAG检索不到相关文档的处理方案]]） |

### 7. 一句话总结

Query Rewriting = **检索前把原始 query 改写成更清晰、更贴近文档表述的问题**（含 LLM 改写、Multi-Query、Step-back、HyDE、历史改写等方法），从源头提升召回率与相关性；它解决"用户语言 ≠ 文档语言"的错配，与查询扩展（加词）、混合检索、Rerank 共同构成 RAG 查询理解的工具箱。
