## RAG 与模型微调 Fine-tuning 的差异及选型方法

### 1. 本质区别

RAG 和微调是给大模型"补充能力"的两条不同路径，切入点完全不同：

| 维度 | RAG（检索增强生成） | Fine-tuning（微调） |
| --- | --- | --- |
| 切入点 | 外挂知识库，检索后塞进上下文 | 改模型参数，把能力/知识/风格压进权重 |
| 改不改参数 | 不改 | 改 |
| 知识载体 | 外部向量库 | 模型权重 |
| 知识更新 | 改知识库即可，即时 | 需重新训练，慢且贵 |
| 解决的核心问题 | "模型不知道"（知识缺失/过时） | "模型不会"（能力/风格/格式/推理方式） |

一句话：**RAG 补"知识"，微调补"能力"。** RAG 的定义与优化作用见 [[29.RAG检索增强生成的定义及对大模型的优化作用]]。

### 2. 全面对比

| 对比维度 | RAG | Fine-tuning |
| --- | --- | --- |
| 知识更新方式 | 更新知识库（增删文档） | 重新训练 + 重新部署 |
| 时效性 | 近实时（入库即可检索） | 滞后（训练周期天/周级） |
| 成本 | 主要是检索 + 推理 token 成本 | 训练算力 + 数据标注 + 部署成本 |
| 算力需求 | 低（推理即可） | 高（需 GPU 训练） |
| 幻觉 | 低（有据可依、可溯源） | 仍可能幻觉，且更难溯源 |
| 可解释性 | 高（能引用来源） | 低（知识在权重里，黑盒） |
| 数据量需求 | 原始文档即可 | 需高质量标注样本（指令-回答对） |
| 上下文窗口压力 | 占用上下文（检索片段） | 不占上下文（知识在权重） |
| 私有数据安全 | 知识库可权限控制 | 微调后知识"泄露"在权重，难收回 |
| 适合的能力 | 事实性知识、动态信息、私有文档 | 领域推理、输出风格、格式遵循、特定任务 |

### 3. 选型方法与决策流程

#### 决策核心：先问"是知识问题还是能力问题"

```
需求 → 是"模型不知道某信息"吗？
        ├─ 是，且知识会变/量大/需溯源 → RAG
        └─ 否，是"模型答得不够好/风格不对/格式不听话"吗？
                ├─ 是 → Fine-tuning
                └─ 两者都有 → RAG + Fine-tuning 结合
```

#### 选型决策表

| 场景特征 | 推荐 |
| --- | --- |
| 知识频繁更新（新闻、政策、内部文档） | RAG |
| 知识量大且需精确引用、溯源 | RAG |
| 私有/机密知识，需权限控制 | RAG |
| 需改变输出风格、语气、格式 | Fine-tuning |
| 需提升特定领域推理/解题能力 | Fine-tuning |
| 需严格遵循复杂输出 schema（JSON/工具调用） | Fine-tuning（或指令微调） |
| 知识固定但推理要求高（医学影像判读等） | Fine-tuning |
| 既需新知识又需领域推理能力 | RAG + Fine-tuning |

#### 何时该结合使用

很多生产场景两者都需要：**微调提升模型的领域推理与遵循能力，RAG 提供实时可溯源的知识。**

| 层 | 作用 |
| --- | --- |
| Fine-tuning | 让模型"会"做这个领域的任务（推理方式、输出格式、术语理解） |
| RAG | 让模型"知道"最新的领域知识（文档、数据、案例） |

> 典型：法律助手——微调让模型会法律推理与文书格式，RAG 接入最新法条和判例。

### 4. 选型常见误区

| 误区 | 纠正 |
| --- | --- |
| "知识不够就微调" | 知识频繁变/量大时微调成本高且无法溯源，RAG 更合适 |
| "RAG 能解决一切" | RAG 改不了模型推理能力和输出风格，能力问题得微调 |
| "微调后就不需要 RAG" | 微调知识会过时且难更新，动态知识仍需 RAG |
| "先微调再说" | 微调成本高、不可逆性强，应先用 RAG + Prompt 验证，确属能力瓶颈再微调 |

### 5. 一句话总结

RAG 与微调的本质区别是"补知识 vs 补能力"：**知识频繁变、需溯源、量大用 RAG；要改风格/格式/领域推理能力用微调；二者常结合（微调提能力 + RAG 供知识）**——选型先判断"是不知道还是不会"，再决定路径。RAG 的局限与定位另见 [[01.简述RAG的定义及核心工作流程+局限性]]。
