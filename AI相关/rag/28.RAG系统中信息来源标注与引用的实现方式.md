## RAG 系统中信息来源标注与引用的实现方式

### 1. 为什么需要来源标注与引用

RAG 的可信度建立在"答案可溯源"上。没有引用，用户无法判断答案是否编造；有了引用，才能核对、追责、信任。来源标注是把"黑盒生成"变成"可审计生成"的关键。

### 2. 实现方式（五步闭环）

#### 第 1 步：chunk 携带完整元数据

切片时就给每个 chunk 打上来源标签，这是溯源的基石（元数据的另一用途——过滤检索，见 [[34.RAG系统利用元数据过滤提升检索精度的方法]]）。

| 元数据字段 | 作用 |
| --- | --- |
| source | 文档名/URL |
| page | 页码 |
| section | 章节/标题路径 |
| chunk_id | 唯一编号 |
| timestamp | 文档时间/版本 |

#### 第 2 步：Prompt 要求模型标注引用编号

把召回的 chunk 编号后送入 Prompt，要求模型对每个事实性结论标注 `[编号]`：

```text
【参考资料】
[1] (来源:员工手册.pdf, p.12) 年假按工龄计算...
[2] (来源:考勤制度.docx, p.3) 调休需提前3天申请...
【问题】年假怎么算？调休怎么申请？
【要求】每个结论后标注来源编号，如 [1]。
```

#### 第 3 步：后处理把引用编号映射回原始 chunk

模型输出带 `[1][2]` 后，后处理解析编号，映射回对应 chunk 的完整元数据（来源/页码/段落），组装成结构化引用列表。

```json
{
  "answer": "年假按工龄计算[1]；调休需提前3天申请[2]。",
  "citations": [
    {"id": 1, "source": "员工手册.pdf", "page": 12, "text": "年假按工龄计算..."},
    {"id": 2, "source": "考勤制度.docx", "page": 3, "text": "调休需提前3天申请..."}
  ]
}
```

#### 第 4 步：前端高亮 + 点击跳转源文档

- 答案中的 `[1]` 渲染成可点击角标。
- 点击展开对应 chunk 原文，或跳转到源文档对应页码/段落。
- 支持高亮命中文本，让用户一眼核对。

#### 第 5 步：强制校验（防幻觉的关键）

| 校验项 | 判定 |
| --- | --- |
| 引用编号是否在召回集内 | 不在 → 删除该句或判幻觉 |
| 引用 chunk 是否真支持该结论 | 不支持 → 标记/重生成（可用 NLI 模型核对） |
| 是否有结论句无引用 | 无引用的事实句 → 标黄警示或剔除 |

> 第 5 步是引用"可信"而非"装饰"的分水岭：没有校验的引用只是格式好看，有了校验才能真正抑制幻觉（见 [[27.RAG系统幻觉问题的实用解决方法]]）。

### 3. 引用格式设计

| 格式 | 示例 | 特点 |
| --- | --- | --- |
| 行内角标 | 年假按工龄计算¹ | 简洁，阅读友好 |
| 编号标注 | 年假按工龄计算[1] | 易解析，工程常用 |
| 脚注式 | 句末[1]，文末列来源 | 适合长文 |
| 结构化字段 | answer + citations JSON | 适合程序消费/API |

### 4. 与溯源、可信度的关系

```
元数据齐全 → 可标注 → 可映射 → 可跳转 → 可校验 → 可信
   基石       生成侧    后处理     前端      防幻觉    最终目标
```

任一环节缺失，可信度链就断：没元数据→无法溯源；没校验→引用可能造假；没前端→用户看不到出处。

### 5. 一句话总结

RAG 的来源标注与引用是一个**"元数据打底 → Prompt 要求标注 → 后处理映射 → 前端跳转 → 强制校验"** 的五步闭环，它让答案从"模型说啥是啥"变成"每句都可追到原文"，是 RAG 可信度的核心实现。流程定位见 [[04.详解RAG的完整工作流程]]。
