## 详解 RAG 的完整工作流程

RAG 的完整工程链路分 **离线索引** 和 **在线问答** 两大阶段，共 7 个关键环节。

```
【离线】 文档加载 → 切片 → 向量化 → 入库（向量库 + 全文索引）
【在线】 查询理解 → 检索（多路召回）→ Rerank → 上下文组装 → LLM 生成 → 后处理/溯源
```

### 1. 文档加载与预处理（Ingestion）

把原始知识灌进系统的第一步，决定了后续一切的上限。

| 子步骤 | 说明 |
| --- | --- |
| 格式解析 | PDF/Word/HTML/Markdown/Excel/PPT 各有解析器；PDF 尤其难（多栏、表格、图片、扫描件） |
| 结构还原 | 标题层级、页码、表格编号、图注、段落边界要保留，便于切片与溯源 |
| 清洗 | 去页眉页脚、去水印、去乱码、统一编码；扫描件走 OCR |
| 元数据标注 | 来源、时间、作者、章节、权限标签——后续过滤和溯源全靠它 |

> PDF 的处理是工业级 RAG 的重灾区，详见 AI提效目录的《02.Agent的Rag遇到pdf怎么处理》。

### 2. 切片（Chunking）

把长文档切成适合向量化与检索的小片段。**切片质量直接决定召回质量。**

| 切片策略 | 说明 | 适用 |
| --- | --- | --- |
| 固定长度 | 按字符/token 数切，简单粗暴 | 快速起步，易切断语义 |
| 滑动窗口 | 固定长度 + overlap，避免边界丢信息 | 通用默认 |
| 语义切片 | 按标题/段落/句子边界切，保语义完整 | 结构化文档（推荐） |
| 父子文档 | 检索用小切片（子），生成时回填大上下文（父） | 兼顾召回精度与上下文完整 |
| 表格/图表单独处理 | 表格结构化、图表生成文字摘要 | 含表格的文档 |

关键参数：chunk_size（如 256~512 token）、overlap（如 10%~20%）、切分符（优先按标题/段落）。

### 3. 向量化与入库（Embedding & Indexing）

| 子步骤 | 说明 |
| --- | --- |
| Embedding 模型 | 把文本映射成稠密向量；中文常用 bge-large-zh、m3e，英文 ada/text-embedding-3 |
| 向量入库 | 存入向量库（Milvus/Qdrant/Pinecone/Weaviate/pgvector），建 ANN 索引（HNSW/IVF） |
| 全文索引 | 同时建 BM25/倒排索引，支撑混合检索（见 [[03.混合检索的定义及在大模型应用中的核心作用]]） |
| 元数据入库 | 切片元数据（来源、页码、章节）一并存，支持过滤检索 |
| 增量更新 | 新文档走相同管道增量入库，避免全量重建 |

### 4. 查询理解（Query Understanding）

用户原始问题往往"又短又糙又带指代"，直接检索效果差，需先加工。

| 技术 | 作用 |
| --- | --- |
| 查询改写（Query Rewriting） | 把口语化/省略的问题改写成更利于检索的完整表述 |
| 查询扩展（Query Expansion） | 补同义词、相关词，扩大召回面 |
| 多查询生成（Multi-Query） | 让 LLM 生成多个等价问法，各路检索后合并 |
| HyDE | 先让 LLM 假设一个答案，用"伪答案"去检索（答案比问题更接近文档表述） |
| 历史改写 | 多轮对话中把"它/那个"还原成实体，解决指代问题 |
| 意图识别/路由 | 判断是否需要检索、走哪个知识库、是否该转 Text-to-SQL |

### 5. 检索（Retrieval）

| 环节 | 说明 |
| --- | --- |
| 多路召回 | 向量检索 + BM25 关键词检索 +（可选）图检索/SQL，混合检索融合 |
| 元数据过滤 | 先按来源/时间/权限过滤，再相似度检索，提升精度与安全 |
| 召回量 | top-N（如 50~100），宁多勿少，交给 Rerank 精筛 |

### 6. 重排（Rerank）

对召回结果用 Cross-Encoder / LLM 精排，取 top-K（3~10）真正相关的片段。

- 详见 [[02.RAG中Rerank的含义及实现方式]]。
- 可叠加阈值过滤，丢弃低相关片段，防噪声污染上下文。

### 7. 上下文组装与生成（Context Assembly & Generation）

| 子步骤 | 说明 |
| --- | --- |
| 上下文拼装 | 把 top-K 片段 + 元数据（来源/页码）+ 用户问题拼成 Prompt |
| 上下文管理 | token 超限时截断/压缩/摘要；注意顺序（lost-in-the-middle 问题，重要信息放首尾） |
| Prompt 设计 | 明确要求"仅依据提供的上下文回答，无关则说不知道"，降低幻觉 |
| LLM 生成 | 调用大模型生成答案，可流式输出 |
| 引用溯源 | 要求模型标注每句结论来自哪个片段/页码，前端高亮可点击 |

### 8. 后处理与评测闭环

| 环节 | 说明 |
| --- | --- |
| 答案校验 | 引用内容只能来自召回 chunk，强制溯源；检测无依据的断言 |
| 安全过滤 | 敏感信息脱敏、合规审查 |
| 缓存 | 相同/相似 query 命中缓存（语义缓存），降本提速 |
| 评测 | 用 recall@k、MRR、答案准确率、幻觉率等指标量化，迭代切片/检索/Prompt |

### 9. 全流程关键机制总览

| 机制 | 说明 |
| --- | --- |
| 离线/在线分离 | 建库离线做，问答在线做，知识更新不动模型 |
| 多路检索 + Rerank | 混合检索保召回，Rerank 保精度，工业标配 |
| 切片是地基 | 切片不当，后续检索/生成全白搭 |
| 元数据贯穿全程 | 过滤、溯源、权限控制全靠元数据 |
| 评测驱动迭代 | 没有评测集的 RAG 调参都是盲调 |
| 上下文工程 | token 预算、顺序、压缩直接影响生成质量 |

### 10. 一句话总结

RAG 完整流程 = **离线"加载→切片→向量化→双索引入库" + 在线"查询理解→多路检索→Rerank→上下文组装→LLM 生成→溯源后处理"**。其中切片是地基、混合检索+Rerank 是召回两板斧、元数据与评测是工程化落地的护城河。
