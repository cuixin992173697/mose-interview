## RAG 中向量数据库增量更新的实现方式

### 1. 为什么需要增量更新

RAG 的知识库不是一锤子买卖，文档会持续新增、修改、删除。若每次变更都全量重建索引，成本与中断都不可接受：

| 动因 | 说明 |
| --- | --- |
| 知识持续增长 | 企业文档每天新增，全量重建耗时随规模线性/超线性增长 |
| 全量重建成本高 | 重新 embedding 全量文档（API 费用/算力）+ 重建 ANN 索引（训练+建图）|
| 需近实时生效 | 新文档入库后希望分钟级可检索，不能等下次全量重建 |
| 文档会变更/删除 | 旧版需失效，错误信息要及时剔除，避免召回过期内容 |

> 全量重建适合"初始建库"或"定期校准"，增量更新才是日常运维的主力。向量库核心原理见 [[19.向量数据库的核心原理简述]]，工作流程见 [[23.向量数据库的核心工作流程]]。

### 2. 增量更新的挑战

向量库的增量更新比传统数据库难，因为 ANN 索引结构对增删改并不友好：

| 挑战 | 说明 |
| --- | --- |
| 在线插入性能 | 写入时不能阻塞查询，需并发安全；HNSW 插入要做图连接，开销不小 |
| 删除/修改难 | 多数 ANN 索引不支持物理高效删除，常用"墓碑（tombstone）"标记软删 |
| 索引质量退化 | 增量插入多了，HNSW 图结构变碎、IVF 聚类中心偏移，召回率下降 |
| 一致性 | 写入后是否能立即查到（read-after-write），分布式场景需考虑副本同步 |
| 空间膨胀 | 软删除+碎片累积，磁盘占用持续增长，需后台 compaction 回收 |

#### HNSW vs IVF 的增量特性差异

| 维度 | HNSW | IVF |
| --- | --- | --- |
| 在线插入 | 支持，插入时建图连接，无需重训练 | 插入到最近簇即可，但聚类中心不更新会偏移 |
| 删除 | 软删除为主，物理删除破坏图结构 | 软删除，物理删除相对容易 |
| 索引退化 | 插入多了图变碎、查询变慢，需重建 | 新点堆在少数簇，召回偏，需重训练 |
| 是否需重训练 | 否 | 是（聚类中心需周期性重算） |

详见 [[36.向量索引的构建使用方法及HNSW与IVF的差异]]。

### 3. 实现方式

#### 方式一：追加插入（Append-Only）

最简单的增量——只新增，不删改。新文档 embedding 后直接插入索引。

- HNSW：天然支持在线插入，最常用。
- IVF：插入到最近簇，但长期不重训练会导致召回退化，需定期重建。
- 适用：知识只增不改的场景（日志、新闻归档）。

#### 方式二：软删除 + 后台合并（Tombstone + Compaction）

删除/修改时不立即物理删除，而是打墓碑标记，查询时跳过；后台定期 compaction 物理清理并重建索引片段。

```
删除/修改 → 标记 tombstone（查询时过滤）→ 后台 compaction → 物理删除 + 重建索引段
```

- 优点：写入快、不破坏索引结构。
- 缺点：空间膨胀、墓碑期间查询需额外过滤、compaction 有资源开销。
- 这是 Milvus/Qdrant/Pinecone 等主流向量库的通用做法。

#### 方式三：全量 + 增量混合（定期全量重建 + 日常增量）

工程上最稳的折中：日常走增量（方式一/二），定期（如每周/每月或召回率下降到阈值时）做一次全量重建，消除碎片、重训聚类中心、恢复索引质量。

| 环节 | 频率 | 作用 |
| --- | --- | --- |
| 增量插入/软删 | 实时/近实时 | 日常变更 |
| 后台 compaction | 小时级 | 回收墓碑空间 |
| 全量重建 | 周/月级或触发式 | 消除退化、重训索引、校准质量 |

#### 方式四：CDC 变更捕获（Change Data Capture）

对接上游数据源的变更流（数据库 binlog、对象存储事件、消息队列），自动把"新增/修改/删除"转成向量库的 upsert/delete 操作，实现近实时同步。

```
源数据库 binlog / 对象存储事件 / Kafka → CDC 管道 → embedding → 向量库 upsert/delete
```

- 优点：自动化、近实时、不漏变更。
- 缺点：管道复杂，需处理乱序/重复/失败重试。

#### 方式五：版本化 / 双索引蓝绿切换

对全量重建场景，先在新索引（blue）上构建，构建完成原子切换查询流量到新索引，旧索引（green）下线。避免重建期间服务中断或质量抖动。

- 适合大规模全量重建、索引迁移、schema 变更。
- 代价：双倍存储与构建资源。

### 4. 主流向量库的增量支持

| 向量库 | 增量能力 |
| --- | --- |
| Milvus | 支持 upsert（主键去重覆盖）、软删除、compaction、分区/分片水平扩展 |
| Pinecone | namespace 隔离、upsert、delete by filter/metadata；全托管 compaction |
| Qdrant | 优化器（optimizer）自动分段合并、upsert、删除；写入即查 |
| Weaviate | upsert、batch 写入、周期性 compaction |
| pgvector | 基于 PostgreSQL，增删改走 SQL 事务，重建索引用 `REINDEX` |

### 5. 实践要点

| 要点 | 说明 |
| --- | --- |
| 用稳定主键 | 文档/切片用业务主键（doc_id+chunk_id），upsert 才能正确覆盖而非重复插入 |
| 删除要级联 | 删文档时级联删其所有 chunk，避免孤儿向量被召回 |
| 监控召回退化 | 增量多了 recall@k 下降时触发全量重建 |
| 写后读一致性 | 关键场景确认写入立即可查（flush/刷新策略） |
| 批量写入 | 增量也尽量批量 upsert，减少小写入对索引的冲击 |
| 修改=删+插 | 多数库的"修改"实质是删旧向量插新向量，注意主键一致 |

### 6. 一句话总结

向量库增量更新的工程套路是：**日常用 HNSW 在线插入 + 软删除墓碑 + 后台 compaction 处理增删改，CDC 自动同步上游变更，定期全量重建（蓝绿切换）消除索引退化**——核心是在"近实时生效"和"索引质量不退化"之间用分层策略取得平衡。
