## 多知识库 RAG 中查询效率与准确性的平衡及幻觉抑制方法

### 1. 多知识库 RAG 的特殊挑战

单知识库 RAG 只管"检得准不准"，多知识库 RAG 还要回答"该查哪个库、查几个、怎么合并、冲突听谁的"：

| 挑战 | 说明 |
| --- | --- |
| 不知道查哪个库 | 用户问题可能落在任一库，全查太慢，漏查又召回不到 |
| 检索效率 | N 个库串行检索，延迟随库数线性增长 |
| 跨库证据冲突 | A 库说政策 X，B 库说政策 Y（版本不同/部门口径不一） |
| 召回噪声叠加 | 每个库都 top-k，合并后候选膨胀，噪声更多 |
| 幻觉风险 | 多源信息混入上下文，模型更容易"缝合"出错误结论 |
| 权限隔离 | 不同库有不同访问权限，不能无脑合并返回 |

### 2. 平衡查询效率与准确性

核心思路：**先选库（缩小搜索面）→ 再检索（保证召回）→ 后融合精排（保证精度）**。

#### 策略一：查询路由（Query Routing）——先选库再检索

用 LLM 或分类器判断问题归属哪个知识库，只对目标库检索，省算力、降延迟。

```text
用户问题 → 路由器（LLM/分类器）→ 命中库列表 → 仅对命中库检索 → 结果
```

- 硬路由：选 1 个库，最快但可能漏。
- 软路由：选 top-2~3 个库并行检索，兼顾召回与效率。
- 路由可基于关键词、语义分类、或元数据（如部门标签）。

#### 策略二：并行检索 + 结果融合

对多个库并行检索（而非串行），再用 RRF/加权融合合并，延迟≈单库，召回更全。融合方法见 [[03.混合检索的定义及在大模型应用中的核心作用]]。

#### 策略三：分层检索（先粗后精）

- 粗筛：各库只取少量候选（top-5），快速合并去重。
- 精排：对合并后的候选统一 Rerank，取最终 top-K。
- 兼顾效率（每库少取）与精度（全局 Rerank）。

#### 策略四：按库权重融合

不同库权威性不同，融合时加权（如官方文档库权重 > 内部 wiki > 论坛帖），让可信源优先。

| 策略 | 效率 | 准确性 | 适用 |
| --- | --- | --- | --- |
| 硬路由 | 高（查 1 库） | 中（可能漏库） | 库边界清晰、问题明确 |
| 软路由+并行 | 中高 | 高 | 不确定归属，需兼顾 |
| 分层检索+全局Rerank | 中 | 高 | 候选多、要精排 |
| 按库权重融合 | 中 | 高 | 库权威性差异大 |

### 3. 幻觉抑制方法

多知识库场景幻觉来源更复杂，需多环节布防（系统级方法见 [[27.RAG系统幻觉问题的实用解决方法]]）：

| 环节 | 方法 | 作用 |
| --- | --- | --- |
| 检索后 | Rerank 去噪 | 跨库候选统一精排，剔除低相关片段 |
| 溯源 | 强制来源标注 | 每句结论必须标注来自哪个库/哪条 chunk（见 [[28.RAG系统中信息来源标注与引用的实现方式]]） |
| 冲突消解 | 多源投票 / 时间优先 / 权威优先 | 同一事实多源矛盾时，按"权威源优先→最新时间优先→多数投票"裁决 |
| 答案校验 | 引用核对 | 引用必须落在召回集内，超出即判幻觉 |
| 置信控制 | 低置信拒答 | 多源都低相关或强冲突时，返回"暂无确切答案"而非编造 |
| 上下文隔离 | 按库分块标注 | 拼上下文时用分隔符+库标签，避免模型混淆来源 |

> 冲突消解是多知识库 RAG 区别于单库的难点：单库"检索到就用"，多库"检索到还要判断信谁"。

### 4. 一句话总结

多知识库 RAG 用**查询路由+并行检索+全局 Rerank** 平衡效率与准确性，用**强制溯源+冲突消解+低置信拒答**抑制幻觉——本质是把"选库、合并、裁决"三件事工程化，而非简单地把多个库的结果一股脑塞给模型。
