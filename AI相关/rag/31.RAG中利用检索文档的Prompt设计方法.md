## RAG 中利用检索文档的 Prompt 设计方法

> 本文专讲"检索到的文档如何有效融入 Prompt"。通用提示工程技巧见 [[16.RAG应用中提示工程的设计技巧与实践心得]]。

### 1. 核心目标

检索到的 chunk 不能"原样堆进 Prompt"就完事——要让它被模型**正确理解、严格依据、可溯源**，避免被忽略、被混淆、被过度发挥。

### 2. 设计方法

#### ① 上下文结构化：用分隔符 + 编号标注证据

让模型清楚区分"证据"与"问题"，避免把检索内容当指令执行（提示注入风险）。

```text
【参考资料】
[1] (来源:员工手册,p.12) ...
[2] (来源:考勤制度,p.3) ...
【问题】
年假怎么算？
【要求】
仅依据【参考资料】回答，结论标注[编号]。
```

#### ② 证据排序：重要信息放前面

规避 **lost-in-the-middle** 问题——模型对长上下文首尾记得清、中间易忽略。把最相关的 chunk（Rerank 后 top-1）放最前，次相关放后。

#### ③ 明确约束：仅用提供的文档

```text
- 仅依据【参考资料】回答，不得使用资料外的知识。
- 资料不足以回答时，回答"根据现有资料无法回答"，不得编造。
```

这是抑制幻觉的关键（见 [[27.RAG系统幻觉问题的实用解决方法]]）。

#### ④ 引用要求：每句结论标来源

要求模型对事实性结论标注 `[编号]`，便于后处理溯源（实现见 [[28.RAG系统中信息来源标注与引用的实现方式]]）。

#### ⑤ Token 管理：控量防超限

| 手段 | 作用 |
| --- | --- |
| Rerank 控 top-K | 只留最相关 3~10 条，砍冗余 |
| 提示压缩 | 压缩/抽取 chunk 关键句（见 [[08.提示压缩的定义及在RAG中的应用意义]]） |
| 截断 | 超长 chunk 截断保留前部 |
| 元数据精简 | 只保留必要元数据，去掉冗长字段 |

#### ⑥ Few-shot 示例：示范引用格式

给 1~2 个"问题+资料+带引用答案"的示例，让模型学会引用风格与拒答边界。

#### ⑦ 多文档冲突处理

当召回的多个 chunk 相互矛盾时，明确告诉模型如何裁决：

```text
- 资料冲突时，说明冲突，优先采信更权威/更新的来源。
- 不要把冲突信息缝合成一个错误结论。
```

### 3. Prompt 模板示例

```text
你是一个严谨的知识问答助手。请依据下方【参考资料】回答【问题】。

规则：
1. 仅依据参考资料回答，不使用资料外知识。
2. 每个事实性结论后标注来源编号，如[1]。
3. 资料不足以回答时，回答"根据现有资料无法回答"。
4. 资料冲突时，说明冲突并优先采信更权威/更新的来源。

【参考资料】
[1] (来源:xx, p.x) ...
[2] (来源:xx, p.x) ...

【问题】
{user_question}

【回答】
```

### 4. 方法对照

| 方法 | 解决的问题 |
| --- | --- |
| 分隔符+编号 | 结构混乱、提示注入 |
| 证据排序 | lost-in-the-middle |
| 明确约束 | 模型编造/越界 |
| 引用要求 | 不可溯源 |
| Token 管理 | 超限、成本高 |
| Few-shot | 引用格式不稳 |
| 冲突处理 | 多源矛盾缝合 |

### 5. 一句话总结

RAG 中利用检索文档的 Prompt 设计 = **结构化标注证据 + 重要信息前置 + 强约束仅用资料 + 要求引用 + 控 token + 示例示范 + 冲突裁决**，核心是让模型"看懂、用对、能追"检索到的文档。
