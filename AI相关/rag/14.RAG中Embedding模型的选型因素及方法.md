## RAG 中 Embedding 模型的选型因素及方法

### 1. 为什么选型要慎重
Embedding 模型一旦上线，**历史数据全部已用它编码入库**——换模型意味着全量重新 embedding 重建索引，成本高。所以选型要在上线前充分验证。

- 候选模型清单见 [[13.RAG中常用的Embedding模型]]，原理见 [[12.解读RAG中的Embedding嵌入技术]]。

### 2. 选型因素
| 因素 | 说明 | 取舍 |
| --- | --- | --- |
| 语言匹配 | 中文选中文模型，英文选英文模型，混合选多语言 | 语言不匹配效果断崖式下降 |
| 领域适配 | 通用模型 vs 领域微调模型 | 医疗/法律/金融等领域微调更准，但需数据与成本 |
| 维度 | 768/1024/1536/3072 | 维度高精度好但存储与检索慢；可配合降维 |
| 最大输入长度 | 256/512/8192 token | 长切片场景必须选长输入模型（如 bge-m3 的 8192） |
| 性能 | MTEB/C-MTEB 榜单 + 自有领域评测集 | 榜单作参考，领域评测才是准绳 |
| 成本 | 开源自部署 vs 商用 API | 开源省调用费但要 GPU 运维；商用按量计费 |
| 向量库兼容 | 是否支持该模型输出的维度与距离度量 | 主流向量库都兼容，注意维度上限 |
| 是否支持 instruction | 查询侧加指令（如"为检索生成表示"） | bge/E5 支持，能进一步提升检索精度 |
| 部署与延迟 | 模型大小、推理速度、并发能力 | 在线检索对延迟敏感，需实测 QPS |

### 3. 选型方法 / 流程

```
①定场景 → ②筛语言 → ③初筛候选模型 → ④建领域评测集 → ⑤对比 recall@k/MRR → ⑥看部署成本与延迟 → ⑦定模型
```

#### 步骤细化
| 步骤 | 动作 | 产出 |
| --- | --- | --- |
| ①定场景 | 明确语言、领域、切片长度、QPS 要求、是否私有部署 | 需求清单 |
| ②筛语言 | 按语言过滤候选池 | 3~5 个候选模型 |
| ③初筛 | 查 MTEB/C-MTEB 榜单 + 社区口碑，圈定候选 | 候选短名单 |
| ④建评测集 | 构造 100~500 条 `<query, 正相关文档>` 业务标注对 | 领域评测集 |
| ⑤对比 | 各模型对文档建索引，跑 query，算 recall@k、MRR、nDCG | 效果排名 |
| ⑥看成本延迟 | 实测推理 QPS、显存占用、API 单价 | 成本评估 |
| ⑦定模型 | 综合效果×成本×延迟，选最优 | 最终模型 |

### 4. 评测集怎么搭
- 来源：真实用户 query + 人工标注的正相关 chunk，或从业务日志挖掘。
- 规模：100~500 条够用，覆盖典型与长尾问题。
- 指标：recall@k（召回率，最重要）、MRR（平均倒数排名）、nDCG（考虑排序质量）。
- 评测方法详见 [[09.RAG调优后效果评估的方法及实际应用中的评估标准]]。

```python
# 评测示意：对比两个模型的 recall@5
for model in [model_a, model_b]:
    docs_emb = model.encode(corpus)
    q_emb = model.encode(queries)
    ranks = search(q_emb, docs_emb, top_k=5)
    print(model, recall_at_k(ranks, ground_truth, k=5))
```

### 5. 常见坑
| 坑 | 说明 |
| --- | --- |
| 只看榜单 | 通用榜单不代表业务领域最优，必须用自有数据验证 |
| 忽略输入长度 | 切片超过模型最大输入会被截断，丢信息 |
| 查询文档用不同模型 | 查询和文档必须用同一模型编码，否则向量空间不一致 |
| 忽视 instruction | bge/E5 查询侧要加指令，不加效果打折 |
| 维度过高盲目上 | 3072 维存储与检索成本高，可降到 1024/768 几乎不掉点 |

### 6. 一句话总结
Embedding 选型 = **按"语言→领域→维度→长度→性能→成本"逐层筛选，核心是用自有领域评测集对比 recall@k/MRR，再在效果与成本延迟间权衡定模型**，切忌只看 MTEB 榜单盲选。
