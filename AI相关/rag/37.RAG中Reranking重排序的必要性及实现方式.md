## RAG 中 Reranking 重排序的必要性及实现方式

### 1. 什么是 Reranking

Reranking（重排序）= 在一阶段粗召回之后，用一个更精细的模型对候选片段**重新打分排序**，把最相关的顶到前面，再取 top-K 进 Prompt。

```
查询 → 粗召回 top-N（向量/混合检索）→ Reranking 精排 → top-K → 拼 Prompt
```

> 与 [[02.RAG中Rerank的含义及实现方式]] 互为补充：02 侧重 Bi-Encoder vs Cross-Encoder 原理，本篇侧重"为什么必须做 + 怎么落地"。

### 2. 为什么必须做 Reranking（必要性）

| 痛点 | 没有重排的问题 | 重排如何解决 |
| --- | --- | --- |
| 向量检索精度有限 | Bi-Encoder 独立编码，语义交互弱，top-K 常混入"像但不对"的片段 | Cross-Encoder 联合编码，精排去噪 |
| 召回含噪声 | 混合检索召回多路、含大量弱相关片段 | 重排按真实相关度重新排序 |
| 上下文 token 有限 | LLM 上下文窗口有限，只能塞少量片段 | 重排精选最相关 top-K，把 token 花在刀刃上 |
| 提升答案质量 | 噪声片段干扰生成，诱发幻觉 | 精选高质量证据，生成更准更稳 |
| lost-in-the-middle | 相关片段若排在中间容易被忽略 | 重排把最相关的放前面，缓解该问题 |

一句话：**粗召回保"别漏"，重排保"排对"**——在 token 预算内把最该给 LLM 看的片段挑出来。

### 3. 实现方式

#### 方式一：Cross-Encoder 精排（主流）

把 `[query, doc]` 拼接送入交叉编码器，输出相关性分数，按分排序取 top-K。模型如 bge-reranker、Cohere Rerank、jina-reranker。精度高，是工业首选。

#### 方式二：LLM 作为 Reranker

让大模型对候选列表做 Listwise/Pairwise/打分排序。零样本、懂复杂语义，但贵且慢，适合候选少或精度要求极高。

#### 方式三：规则/特征加权

用 BM25 分、关键词命中、字段权重、时间衰减等特征二次加权，常作补充。

#### 方式四：多模型融合（RRF）

多个 reranker 结果用 RRF 融合排名，兼顾不同模型优势。

### 4. 两阶段架构落地

| 阶段 | 方法 | 返回 | 目标 |
| --- | --- | --- | --- |
| 粗召回 | 混合检索（向量+BM25） | top-N（50~100） | 高 recall，宁多勿少 |
| 精排 | Cross-Encoder / LLM | top-K（3~10） | 高 precision，精选最相关 |

配合关系见 [[03.混合检索的定义及在大模型应用中的核心作用]] 与 [[04.详解RAG的完整工作流程]]。

### 5. 落地实践要点

| 要点 | 说明 |
| --- | --- |
| 候选量配比 | N 取 50~100，K 取 3~10；N 太大重排慢，太小丢召回 |
| GPU 批处理 | Cross-Encoder 逐对 forward，务必 batch + GPU，否则延迟爆炸 |
| 阈值过滤 | 按分数阈值丢弃低相关片段，防噪声进上下文，避免"硬凑 K 个" |
| 缓存 | 热点 query 的重排结果缓存，降本提速 |
| 监控 | 关注重排延迟、重排前后 recall@K 变化，量化收益 |

### 6. 一句话总结

Reranking 是 RAG 检索的"精排层"：**因为向量检索精度有限、召回含噪声、而 LLM 上下文 token 又有限，必须用 Cross-Encoder（或 LLM）对粗召回重新打分，把最相关的片段精选进 Prompt**——粗召回保召回率，重排保精确率，二者配合是工业级 RAG 的标配。
