## RAG 检索中 Top-K 的含义及 K 值的确定方法

### 1. Top-K 的定义

Top-K = **检索时返回与 query 相似度最高的前 K 个结果**。向量检索（或 BM25）对所有文档打分排序后，只取分数最高的 K 个 chunk 作为候选，拼进上下文交给大模型。

```
query 向量化 → 与全库文档算相似度 → 降序排序 → 取前 K 个 → 拼进 Prompt
```

| 参数 | 含义 | 典型取值 |
| --- | --- | --- |
| K | 最终返回给生成阶段的相关文档数 | 3~10 |
| N（两阶段时） | 一阶段召回的候选数，再由 Rerank 筛到 K | 50~100 |

### 2. K 的本质：召回率 vs 噪声 vs 成本的三方权衡

K 不是越大越好，也不是越小越好，它同时影响三件事：

| 维度 | K 增大 | K 减小 |
| --- | --- | --- |
| 召回率（recall） | ↑ 更可能捞到正确 chunk | ↓ 易漏召回 |
| 噪声 | ↑ 不相关 chunk 混入 | ↓ 上下文更干净 |
| Token 成本/延迟 | ↑ 上下文膨胀、生成更贵更慢 | ↓ 省钱省时 |
| 生成质量 | 可能 ↓（噪声干扰、lost-in-the-middle） | 可能 ↓（证据不足） |

### 3. K 太大 / K 太小的具体后果

#### K 太大

| 问题 | 说明 |
| --- | --- |
| 噪声污染 | 不相关 chunk 混入，模型可能被带偏、答非所问 |
| 上下文膨胀 | 输入 token 暴涨，成本与延迟上升（见 [[40.生产环境中RAG系统的性能优化与成本控制方法]]） |
| Lost-in-the-middle | 关键信息埋在长上下文中部时，模型容易忽略（重要信息应放首尾） |
| 知识冲突 | 多个矛盾 chunk 同时出现，模型难取舍 |

#### K 太小

| 问题 | 说明 |
| --- | --- |
| 漏召回 | 正确 chunk 排在第 K 名之后，直接丢失 |
| 证据不足 | 答案需要的多段信息只召回一部分，答案不完整 |
| 抗噪脆弱 | 单个 chunk 质量差时无备选，容错低 |

### 4. K 值的确定方法

#### 方法一：经验起步值

| 场景 | 起步 K |
| --- | --- |
| 通用问答 | 5 |
| 简单事实查询 | 3 |
| 复杂/多跳推理 | 8~10 |
| 配合 Rerank | 召回 N=50~100，精排后 K=3~5 |

先从经验值起步跑通，再用下面方法精调。

#### 方法二：评测集调参（核心方法）

构建评测集，对不同 K 计算 `recall@k` 和 `MRR`，画曲线找拐点：

```
K:        1    3    5    8   10   15   20
recall@k: 0.55 0.78 0.88 0.93 0.95 0.96 0.97
MRR:      0.55 0.72 0.80 0.82 0.82 0.81  0.80
```

- 选 **recall 已接近平台期、但 MRR 不再下降**的 K——上例中 K=5~8 是性价比拐点。
- K 再大 recall 涨幅微小，但 token 成本线性涨，不划算。

> 评测方法详见 [[09.RAG调优后效果评估的方法及实际应用中的评估标准]]。

#### 方法三：结合上下文窗口预算

```
可用 token 预算 = LLM 上下文上限 - 系统 prompt - query - 输出预留
最大 K ≈ 可用 token 预算 / 单 chunk 平均 token
```

实际 K 取"评测拐点"与"预算上限"的较小值。

#### 方法四：配合 Rerank 的两阶段 K

| 阶段 | 取值 | 目的 |
| --- | --- | --- |
| 一阶段召回 N | 50~100 | 保高召回，宁多勿漏 |
| Rerank 精排 K | 3~5 | 保高精度，去噪声 |

两阶段把"召回全"和"排得准"解耦，是工业级 RAG 的标配（见 [[02.RAG中Rerank的含义及实现方式]]）。

#### 方法五：动态 K

按 query 难度/类型动态调 K：简单事实小 K，复杂多跳大 K。可由轻量分类器或规则判断。

### 5. 工程实践要点

| 要点 | 说明 |
| --- | --- |
| 评测驱动 | 别凭感觉定 K，用 recall@k 曲线找拐点 |
| 与 Rerank 配合 | 召回大 N + 精排小 K，兼顾召回与精度 |
| 阈值过滤 | 除 Top-K 外，可设相似度阈值丢弃低分 chunk，防噪声 |
| 上下文预算 | K 受 LLM 上下文窗口与成本预算约束 |
| 监控 | 线上跟踪平均 K、token 消耗、召回命中率，反推 K 是否合理 |

### 6. 一句话总结

Top-K 是检索与生成之间的"流量阀门"：**K 太大则噪声多、成本高、易 lost-in-the-middle，K 太小则漏召回、证据不足**；确定方法是从经验值起步、用评测集的 recall@k/MRR 曲线找拐点、结合上下文预算取较小值，工业上常配合 Rerank 走"大 N 召回 + 小 K 精排"的两阶段。
