## RAG 系统中文档切割的必要性及常用切割策略

> 本文是"为什么切 + 有哪些切法"的一页式速览。分块的深入定义见 [[10.RAG中分块的定义及分块的必要性]]，各策略差异对比见 [[11.RAG中常见分块策略及各自差异]]。

### 1. 为什么必须切割（必要性）

把整篇长文档直接向量化、整篇塞进上下文都不现实，必须切成小片段：

| 必要性 | 说明 |
| --- | --- |
| Embedding 语义聚焦 | 向量模型对短文本语义编码更准，长文本语义被稀释 |
| 上下文窗口限制 | LLM 有 token 上限，长文档整篇塞不下 |
| 检索粒度 | 召回要"精准定位到相关段落"，整篇召回噪声大、浪费 token |
| Token 成本 | 只把相关片段送入 Prompt，而非整篇，省成本 |
| 溯源精度 | 切片带页码/章节，引用能精确到段落 |

### 2. 常用切割策略速览

| 策略 | 思路 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定长度 | 按字符/token 数切 | 简单 | 易切断语义 | 快速起步 |
| 滑动窗口 | 固定长度+overlap | 避免边界丢信息 | 有冗余 | 通用默认 |
| 语义切片 | 按标题/段落/句子边界切 | 语义完整 | 实现稍复杂 | 结构化文档（推荐） |
| 递归切片 | 先按大分隔符，切不开再按小分隔符 | 灵活保语义 | 长度不均 | 通用文档（LangChain 默认） |
| 父子文档 | 检索用小切片，生成回填父上下文 | 兼顾召回精度与上下文完整 | 索引复杂 | 长文档问答 |
| 结构化切片 | 表格/图表单独结构化 | 保结构信息 | 需专用解析 | 含表格文档 |

### 3. 选型建议

| 文档类型 | 推荐策略 |
| --- | --- |
| 纯文本/无结构 | 递归切片 或 滑动窗口 |
| 有标题层级（手册/规范） | 语义切片（按标题） |
| 长文档、需大上下文 | 父子文档 |
| 含表格/报表 | 结构化切片 + 文本切片 |

关键参数：chunk_size（256~512 token 常见）、overlap（10%~20%）、切分符优先级（标题>段落>句子>字符）。

### 4. 一句话总结

文档切割是 RAG 的地基：**因为 embedding 要聚焦、上下文有窗口、检索要粒度、token 要省**，所以必须切；常用策略从固定长度到父子文档按文档结构选型。切片质量直接决定后续检索与生成的上限，流程定位见 [[04.详解RAG的完整工作流程]]。
