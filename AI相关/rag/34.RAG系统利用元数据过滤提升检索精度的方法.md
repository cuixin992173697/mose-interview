## RAG 系统利用元数据过滤提升检索精度的方法

### 1. 什么是元数据过滤

元数据过滤 = 在向量相似度检索**之前或同时**，先按 chunk 携带的元数据（来源、时间、类别、章节、权限等）筛掉不符合条件的片段，再在剩余集合里做相似度排序。

```
全量 chunk → [元数据过滤] → 候选子集 → [向量相似度 top-K] → 最终召回
```

没有元数据过滤时，可能召回一堆"语义像但来源/时间/权限不对"的片段；加上过滤，召回又准又安全。

### 2. 实现方法

#### ① 写入时：给 chunk 携带元数据

切片入库时，除了向量，还要把结构化元数据一并写入向量库：

```python
collection.insert([
    {"id": 1, "vector": emb, "text": "...",
     "source": "员工手册.pdf", "page": 12,
     "category": "HR", "date": "2024-06-01", "acl": ["hr", "manager"]},
])
```

常见元数据字段：来源文件、页码、章节标题、文档类别、发布时间、版本、权限/可见范围。

#### ② 查询时：构造 filter 表达式

用户问题 + 业务条件 → 转成向量库的 filter：

```python
results = collection.search(
    data=[query_vec],
    expr='category == "HR" and date >= "2024-01-01" and "hr" in acl',
    limit=10,
)
```

filter 来源两种：①用户显式条件（"只查 2024 年的 HR 文档"）②自查询（见 [[07.自查询的含义及在RAG中的必要性]]）——让 LLM 从自然语言里自动抽取出结构化过滤条件。

#### ③ 执行：先过滤再相似度

向量库支持两种执行模式：

| 模式 | 说明 | 特点 |
| --- | --- | --- |
| Pre-filter（先过滤） | 先按元数据筛出子集，再在子集上 ANN | 过滤严格、结果准，但子集太小可能丢召回 |
| Post-filter（后过滤） | 先 ANN 召回 top-N，再按元数据筛 | 召回全，但可能筛完所剩无几 |
| 混合打分 | 元数据匹配作为加权项融入相似度分数 | 平滑，但调参复杂 |

主流向量库（Milvus/Qdrant/Pinecone）多采用 pre-filter 或过滤与检索融合的优化策略。

### 3. 元数据过滤的价值

| 价值 | 说明 |
| --- | --- |
| 提升检索精度 | 限定到正确类别/时间范围，噪声片段直接排除，top-K 更相关 |
| 安全与权限控制 | 按 acl/可见范围过滤，保证用户只能检索到有权限的内容 |
| 提升性能 | 缩小搜索空间，ANN 在子集上更快 |
| 支撑溯源 | 元数据（来源/页码）是引用标注的基础（见 [[28.RAG系统中信息来源标注与引用的实现方式]]） |

### 4. 实践要点

| 要点 | 说明 |
| --- | --- |
| 元数据设计要规范 | 字段统一命名、类型一致、必填项明确，否则过滤不可靠 |
| 过滤条件别过严 | 过严会导致候选子集为空或过小，相似度失去比较意义，召回为空 |
| 平衡 filter 与召回 | 可适当放宽 filter 或增大 top-N 再后筛 |
| 过滤字段建索引 | 元数据字段也要建标量索引，否则 pre-filter 全表扫描反而更慢 |
| 与自查询配合 | 让 LLM 自动从问题抽取 filter，降低用户手动构造成本 |

### 5. 一句话总结

元数据过滤是 RAG 检索的"预筛层"：**写入时给 chunk 打好结构化元数据，查询时先按来源/时间/类别/权限过滤再相似度排序**，既提升精度、又支撑权限控制和溯源，是工业级 RAG 不可或缺的一环。
