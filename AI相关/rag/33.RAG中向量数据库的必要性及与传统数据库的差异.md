## RAG 中向量数据库的必要性及与传统数据库的差异

### 1. 为什么 RAG 需要向量数据库

RAG 的检索阶段要在海量文档片段中"按语义相似度"找最相关的 top-K。这件事传统数据库做不了，必须有专门的向量库支撑：

| 需求 | 说明 | 传统库能否满足 |
| --- | --- | --- |
| 语义检索 | 问"怎么退款"要匹配到"退货流程"，词面不同语义相同 | ❌ 不懂语义 |
| 海量向量存储 | 动辄百万~亿级 chunk，每个都是 768/1536 维浮点向量 | ❌ 关系库存得下但查不动 |
| 近似最近邻（ANN） | 在亿级向量里毫秒级找最相似的 K 个 | ❌ 暴力遍历 O(N) 不可接受 |
| 向量+元数据混合查询 | 先按时间/来源过滤，再相似度排序 | 部分支持，但不高效 |

向量数据库就是为"存向量、按相似度查向量"专门设计的存储与检索引擎。

### 2. 向量数据库 vs 传统数据库

| 维度 | 向量数据库 | 传统关系数据库 |
| --- | --- | --- |
| 存储对象 | 高维稠密向量 + 元数据 | 结构化行/列（数字、字符串、日期） |
| 检索方式 | 相似度检索（余弦/L2/内积）+ ANN | 精确匹配、范围查询、JOIN |
| 索引结构 | HNSW / IVF / LSH / PQ 等 ANN 索引 | B+ 树 / 哈希 / 位图 |
| 查询语言 | 向量 + filter 表达式 | SQL |
| 查询结果 | top-K 相似（近似、有误差） | 精确命中（确定性） |
| 检索语义 | "像不像"（语义相似） | "是不是"（精确相等） |
| 适用场景 | 语义搜索、推荐、RAG 检索 | 事务处理、账务、CRM |

核心差异一句话：**传统库回答"哪个等于 X"，向量库回答"哪个最像 X"。**

### 3. 向量库 / 关系库 / 全文检索库三者对比

RAG 里这三类库常配合使用，定位不同：

| 维度 | 向量数据库 | 关系数据库 | 全文检索库（BM25） |
| --- | --- | --- | --- |
| 检索依据 | 语义相似度 | 精确条件 | 词面命中 + 词频统计 |
| 代表 | Milvus / Pinecone / Qdrant | MySQL / PostgreSQL | Elasticsearch / Lucene |
| 擅长 | "换个说法也能找到" | 强一致性事务 | 精确关键词、专有名词 |
| 短板 | 精确字面匹配弱 | 不懂语义 | 不懂同义、跨语言弱 |
| RAG 角色 | 主力语义召回 | 存原始文档/业务数据 | 混合检索的另一路 |

> 工业级 RAG 通常"向量库 + 全文检索库"混合检索（见 [[03.混合检索的定义及在大模型应用中的核心作用]]），关系库存原始文档与业务数据。

### 4. 什么时候该用向量数据库

| 场景 | 是否需要向量库 |
| --- | --- |
| 语义搜索 / 问答检索 / 相似推荐 | ✅ 必须 |
| 精确查 ID、查订单、查库存 | ❌ 用关系库 |
| 纯关键词搜索（文档名、标签） | 可用全文检索库 |
| 图像/音频/代码的相似检索 | ✅ 必须（多模态向量化后） |
| 需要事务一致性 | ❌ 用关系库 |

### 5. 一句话总结

向量数据库是 RAG 的检索底座：**专门存高维向量、用 ANN 索引做毫秒级语义相似度检索**，传统数据库擅长"精确等于"，向量数据库擅长"语义最像"，RAG 中通常向量库 + 全文检索库 + 关系库各司其职、混合使用。
