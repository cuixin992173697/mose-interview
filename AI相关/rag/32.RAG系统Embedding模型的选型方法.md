## RAG 系统 Embedding 模型的选型方法

> 本文讲"怎么一步步选"（操作流程）。选型要考虑哪些因素见 [[14.RAG中Embedding模型的选型因素及方法]]，常用模型清单见 [[13.RAG中常用的Embedding模型]]。

### 1. 选型是个评测驱动的流程

Embedding 模型没有" universally 最优"，只有"在你的数据上最优"。选型本质是：**明确场景 → 圈定候选 → 用领域数据评测 → 综合成本定模型**。

### 2. 选型六步法

#### 第 1 步：明确场景与语言

| 维度 | 要确定 |
| --- | --- |
| 语言 | 中文/英文/多语言 |
| 领域 | 通用/法律/医疗/金融/代码 |
| 文本长度 | 短句 QA / 长文档 |
| 部署方式 | 本地私有部署 / 调 API |

#### 第 2 步：圈定候选模型

按语言与部署方式初筛（清单见 [[13.RAG中常用的Embedding模型]]）：

- 中文本地：bge-large-zh、bge-m3、m3e-large
- 英文/多语言本地：bge-m3、e5-large、gte
- API：OpenAI text-embedding-3、Cohere embed

#### 第 3 步：构建领域评测集

从真实业务中抽样构建 `(query, 相关文档, 不相关文档)` 标注集——这是选型能否落地的前提。评测集质量直接决定选型可信度。

| 评测集要素 | 说明 |
| --- | --- |
| query 多样性 | 覆盖口语/正式/短/长/含专有名词等 |
| 正例 | 与 query 相关的正确 chunk |
| 负例 | 易混淆但不相关的 chunk（难负例） |
| 规模 | 几百到上千条，覆盖业务分布 |

#### 第 4 步：跑指标对比

对每个候选模型，在评测集上计算检索质量指标（指标含义见 [[09.RAG调优后效果评估的方法及实际应用中的评估标准]]）：

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| recall@k | top-k 里命中正例的比例 | 召回能力 |
| MRR | 第一个正例的倒数排名 | 排序质量 |
| nDCG@k | 考虑排序位置的增益 | 综合排序 |
| hit rate | 至少命中一条的比例 | 基础召回 |

#### 第 5 步：评估部署成本与延迟

| 维度 | 考量 |
| --- | --- |
| 模型大小 | 参数量影响显存与推理成本 |
| 向量维度 | 维度高→存储与检索成本高 |
| 推理延迟 | 离线建库可容忍，在线 query 要快 |
| 部署难度 | 本地需 GPU；API 无需运维但有调用费与数据外发 |

#### 第 6 步：综合决策定模型

把"检索质量 + 成本 + 延迟 + 部署约束"放一张决策表加权打分，选综合最优：

| 模型 | recall@5 | MRR | 维度 | 部署 | 综合 |
| --- | --- | --- | --- | --- | --- |
| bge-large-zh | 高 | 高 | 1024 | 本地 GPU | ★★★★★ |
| m3e-large | 中高 | 中 | 768 | 本地 GPU | ★★★★ |
| OpenAI ada | 高 | 高 | 1536 | API | ★★★★ |

### 3. 决策速查表

| 情况 | 倾向选择 |
| --- | --- |
| 中文、私有部署、要精度 | bge-large-zh / bge-m3 |
| 多语言、长文本 | bge-m3 |
| 无 GPU、接受 API | OpenAI text-embedding-3 / Cohere |
| 成本敏感、轻量 | bge-small / gte-small |
| 领域极特殊（医疗/法律） | 通用模型 + 领域微调，或领域专用模型 |

### 4. 常见误区

| 误区 | 正解 |
| --- | --- |
| 只看榜单分数选模型 | 榜单≠你的业务，必须用领域数据评测 |
| 维度越高越好 | 维度高带来存储/检索成本，够用即可 |
| 只评召回不评延迟 | 在线场景延迟不达标再准也没用 |
| 一次性选型不变 | 数据分布变化要定期复评 |

### 5. 一句话总结

Embedding 选型是**评测驱动的六步流程**：明确场景 → 圈候选 → 建领域评测集 → 跑 recall@k/MRR/nDCG → 评成本延迟 → 综合决策——没有万能模型，只有"在你数据上被指标验证过的"最优模型。
