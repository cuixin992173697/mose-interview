## 简述 RAG 的定义、核心工作流程及局限性

### 1. RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）= 检索 + 生成。

核心思想：在调用大模型回答问题前，先从外部知识库（文档、数据库、网页）中检索出与问题相关的片段，把这些片段塞进 Prompt 上下文，再让大模型基于"问题 + 检索到的证据"生成答案。

一句话定位：**用"外挂知识库"补大模型"参数化知识"的短板，让回答既新又准、且可溯源。**

| 对比维度 | 纯大模型（闭卷） | RAG（开卷） |
| --- | --- | --- |
| 知识时效 | 截止训练日期，无法更新 | 实时检索，知识可随时增删 |
| 领域知识 | 通用知识为主，垂直领域弱 | 接入企业私有文档，垂直领域强 |
| 可信度 | 可能"幻觉"编造 | 答案有出处，可溯源引用 |
| 更新成本 | 需重新训练/微调，贵且慢 | 只更新知识库，便宜即时 |
| 知识载体 | 把知识压进权重 | 知识外置，模型只负责推理 |

### 2. 核心工作流程（三段式）

RAG 本质是一个 **"建库 → 检索 → 生成"** 的管道：

```
离线建库：文档 → 切片 → 向量化 → 入向量库
在线问答：问题 → 向量化 → 检索 → 拼 Prompt → LLM 生成 → 答案
```

| 阶段 | 关键动作 | 产出 |
| --- | --- | --- |
| ① 索引（Indexing） | 文档加载 → 切片（chunking）→ 向量化（embedding）→ 存入向量库 | 可检索的知识库 |
| ② 检索（Retrieval） | 用户问题向量化 → 在向量库做相似度检索（top-k）→ 召回相关片段 | 候选 chunk 列表 |
| ③ 生成（Generation） | 把召回片段拼进 Prompt → 大模型基于上下文生成答案 | 带引用的最终回答 |

> 完整工程化流程见 [[04.详解RAG的完整工作流程]]，这里只做宏观简述。

### 3. RAG 的局限性

RAG 不是银弹，工业落地常见这些坑：

| 局限类别 | 具体表现 | 常见缓解手段 |
| --- | --- | --- |
| 检索不准 | 召回不到关键片段，或召回一堆噪声 | 混合检索、Rerank、查询改写 |
| 切片不当 | 答案被切断在两个 chunk 里，语义丢失 | 语义切片、滑动窗口、父子文档 |
| 上下文丢失 | 长文档全局信息（目录、上下文）在切片后丢失 | 给 chunk 加元数据/摘要上下文 |
| 知识冲突 | 检索到的多份证据相互矛盾 | Rerank 排序 + 溯源 + 让模型判断 |
| 实时性盲区 | 知识库更新到检索之间有窗口期 | 增量索引 + 定时刷新 |
| 多轮/指代问题 | "它/那个"指代前文，单轮检索拿不到 | 历史压缩/改写后再检索 |
| 结构化数据弱 | 表格、数字、报表检索效果差 | 表格结构化 + Text-to-SQL |
| 推理能力上限 | 复杂多跳推理仍依赖大模型本身 | GraphRAG / Agent + RAG |
| 成本与延迟 | 多一次检索 + 更长上下文，token 与时延上升 | 缓存、Rerank 精简、上下文压缩 |

### 4. 一句话总结

RAG = 给大模型开卷考试：**检索负责"找对资料"，生成负责"读懂并作答"**。它的价值在于把"知识更新"和"模型能力"解耦，代价是引入了检索这一可能出错的环节——所以工业级 RAG 的核心工程量，几乎都在"如何检索得更准"上。
