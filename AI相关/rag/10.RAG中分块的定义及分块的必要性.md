## RAG 中分块的定义及分块的必要性

### 1. 什么是分块（Chunking）

分块 = 把长文档**切成若干较小的文本片段（chunk）**，每个片段作为独立的检索单元和向量化单元。

```
长文档 → 分块 → [chunk1, chunk2, chunk3, ...] → 各自向量化 → 入库
```

分块是 RAG 离线索引阶段的第一道工序，**直接决定后续检索与生成的质量上限**。

### 2. 为什么必须分块

#### 原因一：embedding 对长文本语义稀释

- Embedding 模型把整段文本压缩成一个固定维度的向量。文本越长，向量要"平均"的信息越多，语义被稀释，变得**模糊不聚焦**。
- 短文本向量更聚焦、更精确地表达单一语义，检索时匹配更准。

| 文本长度 | 向量语义 | 检索效果 |
| --- | --- | --- |
| 整篇文档 | 多语义混合，模糊 | 命中但不精准 |
| 适中 chunk | 单一主题聚焦 | 精准命中 |
| 过短 | 缺上下文 | 命中但信息不全 |

#### 原因二：模型上下文窗口限制

- 即便长上下文模型，也有 token 上限；召回多个整篇文档必然超限。
- 分块后可精准召回"相关片段"而非整篇，控制 Prompt 长度。

#### 原因三：检索粒度与噪声控制

- 整篇检索：一篇文档里只有一小段相关，却把整篇塞进上下文 → 噪声大、信噪比低。
- 分块检索：只召回真正相关的片段 → 精准、省 token。

#### 原因四：生成 token 成本

- 召回内容越少越精，输入 token 越少 → 推理更便宜更快。
- 分块是"用更少 token 传递更相关信息"的前提。

#### 原因五：上下文聚焦

- 生成时模型注意力有限，聚焦相关片段比面对整篇更能答准。

### 3. 不分块会导致的问题

| 问题 | 表现 |
| --- | --- |
| 向量语义模糊 | 长文档向量不聚焦，检索精度低 |
| 召回噪声大 | 整篇召回，无关内容混入上下文 |
| token 爆炸 | 多篇拼接超窗口、成本飙升 |
| 答案跑偏 | 噪声稀释关键信息，模型注意力分散 |
| 无法精细溯源 | 只能定位到"某篇文档"，定位不到具体段落 |

### 4. 分块的核心权衡

分块不是越细越好，要在"语义完整"和"检索精准"间平衡：

| chunk 太大 | chunk 太小 |
| --- | --- |
| 向量语义稀释、检索不精 | 上下文割裂、信息不全 |
| 噪声多、token 费 | 命中率高但答不全 |
| 召回少而粗 | 召回多而碎 |

→ 所以需要合理的分块**策略**与**参数**，详见 [[11.RAG中常见分块策略及各自差异]]。

### 5. 关键参数

| 参数 | 含义 | 经验值 |
| --- | --- | --- |
| chunk_size | 单个片段长度（字符/token） | 256~512 token |
| overlap | 相邻片段重叠量，防边界丢信息 | chunk_size 的 10%~20% |
| 切分符 | 优先按什么切（标题/段落/句子） | 语义边界优先 |

### 6. 必要性总结

| 维度 | 分块带来的收益 |
| --- | --- |
| 向量质量 | 短文本向量更聚焦，检索更准 |
| 检索粒度 | 精准召回相关片段，噪声可控 |
| 上下文管理 | token 可控，不超窗口 |
| 成本 | 输入 token 少，省钱提速 |
| 溯源 | 可定位到具体片段/页码 |

> 分块是 [[04.详解RAG的完整工作流程]] 离线阶段的地基工序；具体策略见 [[11.RAG中常见分块策略及各自差异]]。

### 7. 一句话总结

分块 = **把长文档切成语义聚焦的小片段作为检索单元**，是 RAG 的地基工序——它解决 embedding 长文本语义稀释、上下文窗口限制、检索噪声、token 成本四大问题，分块质量直接决定召回与生成的上限。
